## 0. 直接回答“要不要开发计划文档”

**要，但要小的、只讲交付的。** 两份东西即可，都不要写进 `docs/`（那 9 份是产品/领域/架构基线，已冻结）：

| 产出 | 内容 | 放哪 |
|---|---|---|
| 本文档（执行方案） | 里程碑与门禁、工作包、任务书模板、每任务 DoD、Git 与冻结纪律 | `review/` |
| 任务书（每任务一份，短） | 目标 / 读哪些文档章节 / 改哪些文件 / 验收命令 / 禁止事项 | `review/tasks/NN-xxx.md` |

判断标准很简单：**凡是在冻结基线里已经写清楚的，计划里一个字都不要重写，只写“引用哪一节 + 怎么验收 + 谁做”。** 否则计划本身会成为第二个 SSOT，几轮之后必然和基线打架（这正是 `docs/09` §3 记录过的坑）。

## 1. M0 必须先做：上游接入可行性验证（阻塞一切）

冻结基线已把“采集来自上游 AutoAccounting 模块化核心、账然是宿主”写成前提，但**这条链路尚未被任何一次真实运行验证过**，而它决定后续所有排期。必须先做一个只做验证、不写业务代码的 spike。

必须回答的 4 个问题：

| # | 问题 | 若答案是“否”的后果 |
|---|---|---|
| Q1 | 上游模块的事件能否被第三方宿主应用接收？以什么形式（对外接口/ContentProvider/广播/文件/数据库/进程内）？ | 宿主方案不成立 → 需重估 |
| Q2 | 账然作为独立 APK，需要满足哪些前置条件才能收到事件（LSPosed 作用域、Root、模块启用、包名白名单、签名）？ | 排期与用户首次配置流程全部改变 |
| Q3 | 上游是否要求宿主实现特定接口或协议（上游 README 明确它是“需要配合记账软件使用”的采集模块）？ | 宿主接入面需要重新设计（现 `07` §3.2 只给了账然侧职责） |
| Q4 | 无 Root 的 OCR 模式（无障碍 / Shizuku）能否独立跑通，作为降级路径？ | 降级路径不可用 → 只能手工记账 + 通知渠道 |

**M0 产出**（三者缺一不算完成）：

1. `review/M0-上游接入验证记录.md`：上述 4 问的结论 + 证据（截图、日志、抓到的原始事件样例、上游 commit hash）。
2. 一个可跑的 spike 工程或 spike 模块：把上游事件打印出来并按 `03` §3.1 的 `ExternalRecognitionResult` 字段做映射试验。
3. **门禁决定**：主路径 = LSPosed 模式 / OCR 模式 / 两者；若主路径与 `07` §9 权限矩阵不一致，**先改 `07`+`06` 再进 M1**（走 §7 的文档变更流程）。

> 该 spike 允许不遵守分层架构与测试要求（临时验证代码），但**不得**写入 `app/` 正式目录，验证后删除或移入 `spike/` 并在 M1 前丢弃。

## 4. 给 Coding Agent 的委派规则（写进每份任务书）

### 4.1 任务书必备 7 项（缺一项就不要派发）

```text
1. 任务目标（一句话，可验收）
2. 必读文档：只列相关章节（按 AGENTS.md §2 的“按任务读取”，禁止让它读全部）
3. 允许修改的文件/目录白名单
4. 明确禁止：不得修改 docs/01–09、README、AGENTS.md、prototype；不得新增业务规则
5. 验收命令（编译 / 单测 / 指定测试类）
6. 验收判据：引用 docs/08 的具体条目编号
7. 交付物：代码 + 测试 + 一段“我做了什么、我怎么验证的”说明
```

### 4.2 规模红线（对齐 AGENTS.md §8）

- **单任务 ≤ 8 个核心文件**（留 2 个余量给修复），超过就拆。
- 触发下列任一项时，任务书里必须写“影响范围说明”，且不得在同一个任务里混做：
  改 `03` 核心领域模型 / 改 Transaction 状态 / 改 pipeline / 改数据库结构 / 改去重策略 / 引入新核心依赖 / 改 AutoAccounting 集成边界。
- 一个任务只做**一件事**：不允许“顺手重构”“顺手补规则”。

### 4.3 冻结文档纪律（最重要的一条）

- 开发期间 `docs/01`–`docs/09`、`README.md`、`AGENTS.md` 视为**冻结输入**。
- 若开发中发现文档错误或缺口：**停下来，写一份“文档变更提案”**（现象 + 影响 + 建议改法 + 受影响章节），由人确认后再改文档，**再改代码**。
- 禁止 Agent 为了让测试通过而改产品规则（AGENTS.md §10）或改文档措辞。
- 文档改动后必须重跑受影响的验收条目（`docs/09` §3 记录过“章节号引用失效”的坑，改章节顺序要全库复查 `§` 引用）。

## 5. 每个任务的完成定义（DoD，逐层收紧）

| 层 | 要求 | 检查方式 |
|---|---|---|
| L1 编译 | 编译通过，无新增告警级错误 | 构建命令 |
| L2 单测 | 新增/修改逻辑有测试；`08` 对应条目断言全绿 | 测试命令 |
| L3 业务路径 | 关键路径有断言（状态 + reason + 期望值） | `08` 条目编号对照 |

**不允许“完成代码 = 完成任务”**（AGENTS.md §9）。任务书里的验收命令必须是**一条能跑的完整命令**，不接受“我本地试过了”。

## 6. 工程与 Git 执行细节

### 6.1 分支与提交

- `main` 只接受里程碑出口（M1…M5）的合并。
- 每个任务一个分支：`feat/wp2-room-schema` / `fix/...`。
- 提交信息前置 WP 编号，便于回溯验收：`WP2: 建立 Transaction 实体与 Room schema`。
- **文档与代码分开提交**：文档变更单独一个 `docs:` 提交，且必须先于受影响代码的提交。

### 6.2 派生风险：baseline 与上游的耦合

- 记录上游 AutoAccounting 的 commit hash 或版本（`07` §22 升级原则要求独立验证 Adapter）。
- 上游升级 = 单独任务 + 重跑 `08` §15/§16，不允许和其他功能混在一个提交里。

### 6.3 建议尽早加的两道保险

1. **采集健康度检测**（`07` §19 + `08` §14 已定义为必须实现，不是可选优化）：自动记账开启且连续 24 小时无任何捕获事件 → 状态置“疑似失效”并在首页与自动记账页提示。防的是“hook 静默失效导致漏账”这种最伤信任的故障。
2. **Decision 规则表驱动测试**：`03` §16 的十条规则每条一个用例（含顺序短路），用表驱动，改规则时一次跑全。

### 6.4 建议固定下来的“验收命令”

```text
./gradlew :app:assembleDebug :app:testDebugUnitTest :app:connectedDebugAndroidTest
```

用一条聚合任务（Gradle custom task 或脚本）把“编译 + 单测 + androidTest”串起来，任务书里只写这一条，避免每次让 Agent 自由发挥验收方式。

## 7. 文档变更流程（开发期间唯一允许改文档的路径）

```text
发现文档缺口/错误
   ↓
写提案（现象 / 影响面 / 建议改法 / 受影响章节清单 / 需重跑的验收条目）
   ↓
人确认 → 改文档（单独 docs: 提交）→ 全库复查 § 引用
   ↓
重跑受影响验收条目 → 再改代码
```

触发“必须写提案”的典型场景：同一事实在两份文档取值不同（`docs/09` §3）、§ 引用失效、`08` 某条判据无法判定、上游能力与 `07` §9 权限矩阵不符。

## 9. 给你的三条判断准则（避免“派了活却验收不了”）

1. **凡是任务书里写不出 `docs/08` 条目编号的，就不是可验收任务**，先补判据再派活。
2. **凡是 Agent 说“文档没写所以我自己定了”的，一律回退**——按 §7 走提案，这正是 AGENTS.md §1“不猜业务规则”的红线。
3. **凡是触发 §4.2 规模红线的任务，先拆再派**；批量大改（>10 核心文件）在这个项目里几乎必然引入与冻结基线不一致的实现。
