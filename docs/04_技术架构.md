# 04 技术架构

版本：v0.1  
定位：本文件定义层边界、依赖方向与禁止事项。领域规则与决策见 `03`，采集与识别集成见 `07`。本文件不重复定义业务规则。

## 1. 技术基线

- Kotlin
- Android 16 / API 36（`targetSdk = 36`）
- `compileSdk = 37`（依赖侧硬要求：AndroidX / Compose 新构件要求依赖方至少 compile 到 API 37；`targetSdk` 仍为 36，运行时行为不变）
- minSdk 31
- Java / JVM target **21**
- Jetpack Compose
- Material 3
- Room
- Hilt
- Coroutines
- Flow / StateFlow
- WorkManager
- Navigation Compose
- DataStore（仅用于设置项）

构建工具链（编码基线，随实现演进更新）：

- Gradle 9.x + Android Gradle Plugin 9.x
- Kotlin 由 AGP 内建（**不使用** `org.jetbrains.kotlin.android` 插件）
- 注解处理统一 KSP；依赖注入 Hilt
- 依赖与版本唯一来源为工程的 `gradle/libs.versions.toml`

架构方向：清晰的 UI / Data 分层 + Repository + Coroutines/Flow + UDF；Compose 侧状态向下、事件向上。

## 2. 总体架构

```text
┌──────────────────────────────┐
│            UI                │
│        Jetpack Compose       │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ ViewModel / StateHolder      │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ UseCase / Domain             │
│ （含 Normalize / Confidence  │
│   Dedup / Decision）         │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Repository                   │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Room / DataStore             │
└──────────────────────────────┘
```

自动记账（采集与识别来自上游模块）：

```text
上游 AutoAccounting 模块（Capture / Hook / Accessibility / OCR / SMS / 外部规则匹配）
          ↓  （不得写账然数据库）
     capture/ 适配层
          ↓
   NotificationEnvelope / ExternalRecognitionResult
          ↓
   autoaccounting/ Adapter
          ↓
   TransactionCandidate + CaptureEvidence
          ↓
   Domain：Normalize → Confidence → Dedup → Decision
          ↓
   Repository → Room
```

约束：

- 上游模块与账然之间只有一个接入面：`capture/` + `autoaccounting/`。
- 领域决策（Pending / Confirmed / Duplicate / ClearlyInvalid）只能发生在 Domain。
- **账然不自建第二套采集实现**；Android 侧的 NotificationListenerService 不是 v0.1 的采集主体（通知采集来自上游模块的工作模式）。

## 3. 目录与职责

```text
app/                          // 账然 APK（单 APK 交付）
├── ui/
│   ├── theme/
│   ├── components/
│   └── screen/
├── domain/
│   ├── model/
│   ├── service/          // Normalize / Confidence / Dedup / Decision
│   └── usecase/
├── data/
│   ├── local/            // Room、DAO、DataStore（账然自有库）
│   ├── repository/
│   └── mapper/
├── capture/              // 采集接入层：接收采集核心产出，构造 Envelope / 原始结果
├── autoaccounting/       // 采集核心产出 → TransactionCandidate + Evidence 的 Adapter
├── backup/               // 备份导出/导入、恢复三模式、版本迁移
├── log/                  // 捕获日志与证据存储、保留策略、脱敏
└── common/

:capture                      // 内嵌采集核心（AutoAccounting，GPL-3.0，独立 Gradle 模块，D6）
                              // 含其采集 / 识别 / 规则 / AI 与 UI；自带独立 Room 库（D4）
```

职责说明：

- `capture/`：采集接入层，只负责“接收 + 保真 + 标记来源”。不解析业务语义，不写交易，不修改采集核心数据。
- `autoaccounting/`：只负责“屏蔽上游模型 + 转换为统一候选 + 生成证据”。不做领域决策。
- `:capture`（内嵌采集核心）：提供采集与识别能力；**不得**持有账然 Repository / DAO 引用、不得直接写 `transactions`、不得决定状态；其 UI 仅作悬浮窗 / 记账面板入口（`07` §16）。
- `backup/`：负责备份格式、校验、迁移与恢复事务；不直接操作 DAO 之外的层；只覆盖账然账务数据（D4）。
- `log/`：负责捕获日志与证据的写入、保留策略、脱敏；对外只读。

**内嵌采集核心约束**：以 Gradle 模块形式内嵌（`07` §21 的 D6-a→b→c）；来源与 commit 必须记录（`10` §1，纪律见 `07` §20，升级流程见 `07` §22）；两套 Room 库文件必须隔离（D4）。

枚举与领域值对象的落点纪律（防止同一枚举出现两处定义）：

- 所有领域枚举（`TransactionType`、`TransactionState`、`CaptureSource`、`AccountType`、
  `PaymentChannel`、`BudgetScope`、`Currency` 等）**只在 `domain/model/` 定义一次**。
- 其它层只能**引用**，不得复制定义：
  - `data/local/entity` 可以直接依赖 `domain/model` 的枚举（data → domain 是允许方向）；
  - `autoaccounting/`（Adapter）与 `capture/` **不得**定义领域枚举，只能 import；
  - 禁止 data/local → autoaccounting 的依赖方向（实体不得依赖 Adapter 层）。
- 若某枚举在编码早期被临时定义在非 `domain/model` 位置，应在该枚举首次被 `data/` 层需要时
  迁移到 `domain/model/`，并由引用方改为 import（属一次性搬迁，不是"改上游逻辑"）。

如果项目规模增长，再拆 Gradle module；v0.1 不拆。

## 4. UI 层

UI 只负责：

- 展示状态
- 接收用户操作
- 发送事件

UI 不直接：

- 访问 DAO
- 修改数据库
- 执行业务规则
- 计算相似度、置信度、统计口径以外的业务判断（统计口径由 Domain 提供，UI 只做格式化展示）

ViewModel / StateHolder：

- 管理页面状态
- 调用 UseCase
- 暴露 StateFlow
- 接收 UI Event

Composable 不接收整个 ViewModel，只接收需要的 state 与 event。

## 5. Domain 层

负责：

- Transaction 业务规则
- Normalize
- Confidence
- Dedup
- **Decision（决定 Pending / Confirmed / Duplicate / ClearlyInvalid）**
- Refund
- Transfer
- 用户修改保护（FieldEdit）
- 统计口径计算

Domain 不应该依赖 Compose，也不应该依赖 Android framework 类型。

## 6. Data 层

负责：

- Room（账务数据唯一事实来源）
- DAO
- Repository
- Data Mapper
- DataStore（仅设置项）
- Backup storage（文件读写与校验）

存储归属：

| 数据 | 存储 |
|---|---|
| transactions / categories / accounts / budgets / rules / field_edits | Room |
| capture_logs / evidence / duplicate_decisions | Room |
| 设置项（开关、主题、阈值、工作模式） | DataStore |
| 备份文件 | 应用私有目录文件 |

Repository 是 UI / Domain 访问数据的边界。UI 与 Domain 都不得直接持有 DAO。

## 7. Database

Room 作为本地事实来源。

必须：

- 使用 migration
- 不允许无条件 destructive migration
- 数据库 schema 变化必须有 migration
- migration 必须测试
- `exportSchema = true`，schema JSON 必须入库到版本控制

v0.1 的 migration 验收形态：初始 schema 导出 + 预留 `v1 → v2` 空迁移用例（见 `08` §9）。

## 8. 自动记账层

采集与识别来自上游 AutoAccounting 模块，账然侧模块不应直接拥有最终 Transaction。

职责：

```text
capture/         接收与保真
autoaccounting/  转换与证据
```

约束：

- 上游输出必须进入统一候选链路，不得跳过 Domain。
- 上游模块不得持有 Repository / DAO 引用（Hilt 不得向上游模块暴露数据层）。
- 自动记账模块不得直接写 Transaction，也不得决定状态。

## 9. 上游采集模块接入

MVP 的采集与识别由**内嵌的采集核心**（AutoAccounting，Gradle 模块）按工作模式提供：

| 工作模式 | 采集来源 | 账然侧接入点 |
|---|---|---|
| ~~LSPosed 模式~~ | Hook 系统通知、Hook 应用内数据 | **内嵌后不支持**（已剥离 Xposed 身份，且目标设备无 Root） |
| OCR 模式 | 无障碍 / Shizuku 截图 | 接收采集核心识别结果 → `capture/` |
| 短信模式（可选） | 短信广播 | 接收采集核心事件 → `capture/` |
| 手工模式 | 用户输入 | 直接走 Domain UseCase，不经采集核心 |

**内嵌采集层需要实现**：

1. 采集核心的初始化与可用性检测（识别服务是否可用、最近是否有事件）。
2. **进程内接口**（`07` §3.5）：采集核心产出经 `capture/` 接入层交给领域层——不再有 URI scheme 与接收入口 Activity。
3. 事件落点：接收 → 落 `capture_logs` / `evidence` → 生成候选。
4. 权限与模式引导（按 `07` §9 的权限矩阵；引导对象是**本应用**）。
5. 失败隔离：采集核心异常不得导致账然数据库不可用或 UI 崩溃。

采集核心的启动约束：

- 采集核心必须**延迟初始化**且**允许失败**：其初始化异常不得导致 Application 启动失败。
- 采集核心的失败边界止于“自动捕获不可用”，不得向上传播为 App 不可用。
- 手动记账链路（UI → ViewModel → Domain → Repository → Room）**不得依赖采集核心的任何类型或初始化状态**。

### 9.1 采集接入层的架构约束

- 采集核心产出**必须经进程内接口**交给领域层（`07` §3.5）；不得绕过接口直接落库。
- **不得**直接写 `transactions`、**不得**决定 Pending / Confirmed（决策只在 Domain，`07` §3.4）。
- 采集核心不得持有账然 Repository / DAO 引用；两套 Room 库文件隔离（§9.2）。
- 采集核心的 UI（悬浮窗 / 记账面板）不得进入账然导航图（`07` §16）。

### 9.2 采集核心关系与隔离

- 采集核心以 **Gradle 模块内嵌**于账然 APK（D6）：同进程、同 APK，但**领域边界由进程内接口约束**。
- **Room 库文件必须隔离**（D4）：两套库文件名不同、互不 import、互不查询；备份只覆盖账然账务数据（`02` §17）。
- 采集核心**不得持有账然 Repository / DAO 引用**。
- 权限由**账然 APK 自身声明**（含 `INTERNET`，仅本机回环；见 `07` §9）。
- 不得声明不必要的可导出组件。

禁止：

- 采集核心直接写 Room。
- 账然在 v0.1 另建第二套采集实现（含自建 NotificationListenerService 作为采集主体）。
- 把采集核心的原始 UI 作为账然页面入口（唯一例外：悬浮窗 / 记账面板）。

## 10. 无障碍能力

由上游模块按 OCR 模式提供，账然侧只消费结果。

原则：

- 最小权限
- 最小读取范围
- 不持续扫描无关页面
- 结果仍必须进入统一 Candidate pipeline

## 11. OCR

由上游模块按 OCR 模式提供。

截图原则：

- 临时保存
- 完成后删除
- 不默认上传
- 不进入备份包

## 12. AI

AI 是可选能力，由上游模块提供，默认关闭。

流程：

```text
Raw Capture
 ↓
AI（上游）
 ↓
Structured JSON
 ↓
Schema Validation
 ↓
Domain Validation
 ↓
Dedup
 ↓
Decision
 ↓
Pending / Confirmed
```

AI 不拥有最终记账权限。

## 13. WorkManager

适合：

- 自动备份
- 清理日志（按保留策略）
- 后台维护任务
- 采集健康度检查（连续无捕获检测）

不用于代替实时采集事件。

## 14. 前台服务

不要为了“保证自动记账”而默认永久启动 FGS。

采集应优先使用上游模块与系统提供的事件入口。

## 15. Navigation

采用单 Activity + Compose Navigation。

Screen 不应直接互相持有。

通过 route / navigation event 进行跳转。

## 16. 状态管理

统一：

```text
UiState
UiEvent
UiEffect
```

命名示例：

```text
HomeUiState
HomeEvent
HomeEffect
```

约定：

- `UiState` 必须是不可变数据类，可序列化用于进程重建恢复。
- `UiEffect` 只用于一次性事件（导航、Toast、Snackbar），不得用于承载业务状态。
- 业务状态不得存放在 Activity 或 Composable 局部变量中。

## 17. 错误处理

错误分类与处理归属：

| 错误类型 | 归属层 | 用户可见结果 |
|---|---|---|
| 用户输入错误 | Domain 校验 | 字段级错误提示，不落库 |
| 数据错误（约束冲突、脏数据） | Domain / Repository | Error State + 可操作恢复建议 |
| 捕获错误（上游不可用、事件格式异常） | capture/ | 捕获日志 FAILED + 自动记账状态提示 |
| 识别错误（上游识别失败/超时） | autoaccounting/ | 候选标记不完整 → Pending 或日志 |
| 数据库错误（磁盘满、写入失败） | Repository | Error State，数据不变，可重试 |
| 权限错误 | capture/ + UI | 权限状态提示 + 引导页入口 |
| 外部引擎错误 | autoaccounting/ | 隔离：不影响 DB 与 UI，写日志 |

统一约束：

- UI 不显示内部异常堆栈。
- 任何错误都不得导致账务数据被静默丢弃；无法判断时进入 Pending 或写捕获日志。
- 失败必须可重试或有明确终态。

## 18. 日志

不得记录：

- 完整支付通知原文
- 完整账号
- 完整手机号
- 完整银行卡信息
- 身份证号
- API Key
- 密码

Debug 模式也应默认脱敏。

脱敏字段清单以 `02` §20 为准，`log/` 模块负责实现。

## 19. 依赖原则

优先：

- AndroidX
- Jetpack
- Kotlin 官方生态

不要因为一个小功能引入大型依赖。

引入新的核心依赖前必须说明影响范围（见 `AGENTS.md` §8）。

## 20. 架构纪律与禁止事项

禁止：

```text
Composable → DAO
Composable → Room
UI → 自行计算相似度/置信度/状态
Parser → DAO
Parser → Transaction
内嵌采集核心 → Room（账然库）
内嵌采集核心 → 决定 Pending / Confirmed
内嵌采集核心 → 绕过接口直接落库
接收入口 Activity → 解析 / 映射 / 落库（入口已随 D7 删除，此处保留为"禁止复活"）
AutoAccounting → Room
AI → Transaction
Activity → 保存业务状态
同一业务对象存在两个编辑入口
同一业务结论在两个层分别计算
```

推荐：

```text
UI → ViewModel → Domain（含 Decision）→ Repository → Room
采集核心产出（进程内接口）→ capture/ → autoaccounting/ Adapter → Candidate → Domain → Repository
```

架构纪律条款：

1. **唯一决策点**：Pending / Confirmed / Duplicate / ClearlyInvalid 只能由 Domain 的 Decision 环节产出。
2. **唯一编辑入口**：每个业务对象只有一个 UI 编辑入口（分类只在分类页、规则只在规则页、交易字段只在详情页字段级编辑）。
3. **唯一计算处**：去重结论、置信度、统计口径只在 Domain 计算；UI 只展示 Domain 已给出的结论，不自行推导。
4. **禁写边界**：内嵌采集核心、Parser、UI 均不得写账然数据库或创建最终 Transaction。
5. **唯一接入面**：与采集核心的所有交互只经 `capture/` + `autoaccounting/`；采集核心以 Gradle 模块内嵌，无独立补丁仓（`07` §2.1 已废弃）。
6. **采集核心产出不得绕过接口直接落库**：产出必须经进程内接口交给领域层（`07` §3.5），不得直接写 Room 或决定状态。
