## 记录 1 · T4 接收入口真机验证（2026-10-10）

### 1.1 环境

| 项 | 值 |
|---|---|
| 机型 / 系统 | 小米 14（`23127PN0CC`）/ HyperOS，Android 16（API 36） |
| 连接方式 | 无线调试 `192.168.133.20:38907` |
| 应用 | `com.zhangran.app` debug 构建（含 T2b 的 Room 落库与应用级提交作用域） |
| 判定方式 | **把设备上的 Room 库拉到本地用 `sqlite3` 读取**（真机无 `sqlite3` 命令，`run-as` 也无法直接查库） |

### 1.2 执行过的命令（原样）

```bash
adb -s 192.168.133.20:38907 install -r app/build/outputs/apk/debug/zhangran-debug.apk

# ① 版本正确 + 合法载荷（载荷 Base64URL 内容：{"money":26.5,"phone":"13812345678","merchant":"全家"}）
adb shell am start -a android.intent.action.VIEW \
  -d "zhangran://capture?v=1&payload=eyJtb25leSI6MjYuNSwicGhvbmUiOiIxMzgxMjM0NTY3OCIsIm1lcmNoYW50Ijoi5YWo5a62In0"

# ② 版本不受支持
adb shell am start -a android.intent.action.VIEW \
  -d "zhangran://capture?v=2&payload=eyJtb25leSI6MjYuNSwicGhvbmUiOiIxMzgxMjM0NTY3OCIsIm1lcmNoYW50Ijoi5YWo5a62In0"

# ③ 非法载荷
adb shell am start -a android.intent.action.VIEW \
  -d "zhangran://capture?v=1&payload=@@@invalid@@@"

# 边界：只有 scheme+host（无查询串）
adb shell am start -a android.intent.action.VIEW -d "zhangran://capture"

# 边界：未声明的 host（应不可解析）
adb shell am start -a android.intent.action.VIEW -d "zhangran://other?v=1"
adb shell am start -a android.intent.action.VIEW -d "zhangran://captureX?v=1"
```

### 1.3 三种输入的实际结果（真机库中记录）

| 输入 | 期望（`docs/07` §3.5） | 实测 `capture_logs.status` | 实测 `reason` |
|---|---|---|---|
| ① `v=1` + 合法载荷 | ACCEPTED | `RECEIVED` | — |
| ② `v=2` + 合法载荷 | VERSION_MISMATCH | `VERSION_MISMATCH` | 载荷版本不受支持：v=2，当前支持 v=1 |
| ③ `v=1` + `@@@invalid@@@` | INVALID_PAYLOAD | `FAILED` | 载荷不是合法的 Base64URL 文本 |
| 边界：无查询串 | 版本缺失 | `VERSION_MISMATCH` | 载荷版本缺失（v 参数未提供） |

> `ACCEPTED → RECEIVED`、`INVALID_PAYLOAD → FAILED` 是 T2b 按 `docs/03` §19 的 11 个取值所做的
> 映射（采集侧 outcome 与日志状态不是同一枚举），语义一一对应。

配套实测值：

```text
PRAGMA user_version              = 2
表数量                            = 9（v1 五张 + v2 四张）
capture_logs 行数                 = 5
capture_evidence 行数             = 5
capture_logs.evidenceId = evidence.id（join 命中）  = 全部命中
transactions 行数                 = 0        ← 本链路只写日志与证据（docs/07 §2）
含完整手机号 13812345678 的行数     = 0        ← 脱敏生效，库中为 138***5678
crash 缓冲                        = 空
dumpsys activity activities | grep zhangran = 空（入口立即结束，finish() 生效）
```

### 1.4 URI 解析（`docs/08` §17.1「scheme 可解析」的设备侧断言）

```bash
adb shell cmd package query-activities -a android.intent.action.VIEW -d "<uri>"
```

| URI | 解析结果 |
|---|---|
| `zhangran://capture?v=1` | ✅ 命中 `com.zhangran.app.capture.CaptureEntryActivity` |
| `zhangran://other?v=1` | ❌ No activities found |
| `zhangran://captureX?v=1` | ❌ No activities found |

结论：`intent-filter` 的 `scheme + host` 过滤**按声明生效**（`docs/07` §3.5 的
`exported=true` + `BROWSABLE` + `host="capture"` 配置正确）。

### 1.5 结论

1. **契约可用**：`zhangran://capture` 在真机上可被系统解析并拉起接收入口（`docs/08` §17.1 的设备侧断言满足）。
2. **HyperOS 未拦截手动拉起**：`am start` 路径下，入口被成功解析、进程被创建、事件被处理并落库。
   因此 `DEVICE_ENVIRONMENT.md` §3.1 所述"后台启动管控"在**手动触发**这一路径上不成立。
3. **仍未验证的路径**：上游应用**以 API 隐式拉起**（`startActivityIfResolvable`）时的后台启动限制。
   该路径受上游是否持有 `SYSTEM_ALERT_WINDOW` / HyperOS「后台弹出界面」权限影响，
   属 M0 联调的实测项，本记录不作结论。
4. **附带验证（T2b §4.5.1）**：真机落库路径为
   `CaptureEntryActivity → CaptureSubmitter（应用级作用域）→ CaptureProcessor → RoomCaptureLogSink`，
   Activity 在提交后立即 `finish()`。若提交仍绑定 `lifecycleScope`，`onDestroy` 会取消在途挂起点，
   上述 5 条记录**一条都不会出现**。记录存在即证明**应用级作用域修复在真机上生效**。

### 1.6 复现方法

```bash
# 1) 安装 debug APK
adb -s <serial> install -r app/build/outputs/apk/debug/zhangran-debug.apk
# 2) 触发（示例为版本正确的合法载荷）
adb -s <serial> shell am start -a android.intent.action.VIEW -d "zhangran://capture?v=1&payload=<Base64URL>"
# 3) 结束进程以触发 WAL checkpoint
adb -s <serial> shell am force-stop com.zhangran.app
# 4) 取出库（run-as 用户不能写 /data/local/tmp，必须让 shell 侧重定向）
adb -s <serial> shell "run-as com.zhangran.app cat databases/zhangran.db > /data/local/tmp/zr.db"
adb -s <serial> shell "run-as com.zhangran.app cat databases/zhangran.db-wal > /data/local/tmp/zr.db-wal"
adb -s <serial> pull /data/local/tmp/zr.db .
adb -s <serial> pull /data/local/tmp/zr.db-wal .
# 5) 本地用 sqlite3 读（同目录下 .db 与 .db-wal 必须同时存在，否则看不到 WAL 中已提交的数据）
sqlite3 zhangran.db "SELECT status, payloadVersion, reason FROM capture_logs ORDER BY capturedAt;"
```
