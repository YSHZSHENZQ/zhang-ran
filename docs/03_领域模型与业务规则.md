# 03 领域模型与业务规则

版本：v0.1  
本文件是领域对象、字段语义、业务不变量、领域决策与去重规则的 Single Source of Truth。其他文档只能引用，不得重复定义。

## 1. 核心领域对象与数据流

v0.1 的采集与识别由上游 AutoAccounting 模块提供，因此数据流只有**一条**：

```text
上游引擎输出（Capture / Recognition Result）
        ↓
Adapter（账然 capture/ + autoaccounting/）
        ↓
TransactionCandidate + CaptureEvidence
        ↓
Normalize（规范化）
        ↓
Confidence（置信度）
        ↓
Dedup（去重）
        ↓
Decision（领域决策，唯一决策点；规则见 §16，顺序短路）
        ├─ 规则 1–10 全部不命中且关键字段齐备且 overallConfidence >= 阈值 → CONFIRMED
        ├─ 命中任一阻断条件（不确定）                                 → PENDING（带 reason 集合）
        ├─ 判重为重复                                                 → DUPLICATE（保留候选与证据）
        └─ 明确无效                                                   → 不创建 Transaction，写 CaptureLog(IGNORED_INVALID)
        ↓
Repository → Room
```

核心对象：

- NotificationEnvelope（仅通知类来源存在）
- ExternalRecognitionResult（上游原始结果）
- TransactionCandidate（含 ParseResult 语义的统一候选）
- Transaction
- Category
- Account
- Budget
- BudgetScope
- CaptureEvidence
- ParsingRule
- DuplicateDecision
- FieldEdit
- CaptureLog

说明：上游引擎内部如何解析不属于账然领域模型；账然不再定义独立的账然侧 `ParseResult` 落库对象，解析信息以 `ParsingRule` + `CaptureEvidence` + 候选字段形式存在。

## 2. NotificationEnvelope

表示“捕获到的原始事件”，仅通知类来源（LSPosed Hook 通知 / 通知渠道）存在。

字段：

```text
captureId
packageName
notificationId
tag
key
postTime
title
text
bigText
subText
infoText
summaryText
tickerText
category
extrasKeys
captureSource
listenerConnectedAt      // 监听/模块连接时间，用于历史回灌隔离
isHistoricalReplay       // 是否在连接后补发的历史通知
```

它只表示事实，不表示已经识别成什么交易。

约束：

- 在监听/模块连接时刻（`listenerConnectedAt`）之前发布的通知视为历史回灌，必须标记 `isHistoricalReplay = true`。
- 历史回灌事件不得直接入账；只能进入 Pending（reason = LOW_CONFIDENCE）或写捕获日志，具体见 `07` §8。

## 3. ExternalRecognitionResult 与 TransactionCandidate

### 3.1 ExternalRecognitionResult

上游引擎的输出，字段以 Adapter 实际接入结果为准，但至少需要提供：

```text
externalId               // 上游记录的稳定标识，可为空
engineVersion            // 上游引擎/规则版本标识，对应 parserVersion
merchant / amount / direction / categoryHint / accountHint
transactionId            // 渠道单号，可为空
transactionTime
confidenceHints
matchedKeywords
rejectedKeywords
rawEvidence              // 上游证据原文或引用
captureSource
```

### 3.2 TransactionCandidate

候选交易不是最终交易，允许字段不完整。

```text
candidateId
merchant            （可空）
amountMinor         （可空）
currency
direction           （可空）
categoryHint        （可空）
accountHint         （可空）
transactionId       （上游渠道单号，可空；落库时映射为 externalTransactionId）
transactionTime     （可空）
confidence          各字段 confidence + overallConfidence
matchedRuleId
engineVersion       （上游引擎/规则版本标识）
matchedKeywords
rejectedKeywords
evidenceId
captureSource
candidateState      CANDIDATE | NORMALIZED | DUPLICATE | REJECTED_INVALID
```

规则：

- 候选不完整不是错误；是否进入 Pending 由 §16 的决策规则决定。
- `direction` 无法确定时，决策结果必须是 PENDING（reason = DIRECTION_UNCERTAIN），不得默认按支出处理。

## 4. 金额

统一：

```text
Long amountMinor      // 货币最小单位（人民币为分）
```

权威换算（人民币）：

```text
¥0.01      -> 1
¥12.34     -> 1234
¥100       -> 10000
¥999999.99 -> 99999999
```

约束：

- `amountMinor >= 0`；方向由 `type` 表达，禁止用负数表达方向。
- 解析阶段允许使用 `BigDecimal`；最终禁止使用 `Double` / `Float` 保存或运算金额。
- 非法金额（无法解析、超出上限、负数）不得产生 CONFIRMED 交易。

## 5. Transaction

最终账务记录。

```text
id                      String（UUID），主键
type                    TransactionType
amountMinor             Long
currency                Currency（v0.1 仅 CNY）
merchant                String?
categoryId              String?
accountId               String?
sourceAccountId         String?        // 仅 TRANSFER
targetAccountId         String?        // 仅 TRANSFER
relatedTransactionId    String?        // 仅 REFUND：原交易 id
transactionTime         Long           // UTC epoch millis
transactionTimeZone     String         // 记录发生时的时区 id
note                    String?
state                   TransactionState
source                  CaptureSource
externalTransactionId   String?        // 渠道单号（上游 transactionId），可空
engineVersion           String?        // 上游引擎/规则版本
matchedRuleId           String?
evidenceId              String?
confirmedByUser          Boolean       // 用户是否确认过（未修改也置 true）
orphan                   Boolean       // 仅 REFUND：原交易已删除
createdAt               Long
updatedAt               Long
deletedAt               Long?          // 软删除时间
```

枚举：

- `TransactionType`：EXPENSE | INCOME | TRANSFER | REFUND
- `TransactionState`：PENDING | CONFIRMED | IGNORED | DELETED | DUPLICATE
- `CaptureSource`：见 `07` §5（SSOT）
- `candidateState`（仅候选阶段）：CANDIDATE | NORMALIZED | DUPLICATE | REJECTED_INVALID，与 `TransactionState` 不是同一枚举

字段约束：

- `id`：UUID 字符串，由账然生成。上游 `externalId` / 渠道单号不得作为主键，只能放在 `externalTransactionId` 并建立非唯一索引。
- `externalTransactionId`：可空；非空时建立索引用于去重。
- 时间：`transactionTime` / `createdAt` / `updatedAt` / `deletedAt` 一律以 UTC epoch millis 存储；展示时按设备当前时区转换。`transactionTimeZone` 记录交易发生时的时区。
- `currency`：v0.1 仅支持 `CNY`。非 CNY 的交易不得自动入账，必须进入 Pending（reason = AMOUNT_UNCERTAIN），并在 v0.1 不提供多币种换算。
- `type = TRANSFER` 时：`sourceAccountId` 与 `targetAccountId` 必填、不得相同、`categoryId` 必须为空、不计入消费统计。
- `type = REFUND` 时：`relatedTransactionId` 必填（无法确定时该记录必须为 PENDING）；`categoryId` 允许为空（分类不明确时）或使用对应支出分类；`orphan = true` 表示原交易已删除或缺失。
- `type = EXPENSE | INCOME` 时：`sourceAccountId` / `targetAccountId` / `relatedTransactionId` 必须为空。

领域约束：

- `merchant` 规范化：去首尾空白、合并连续空白、去除渠道前后缀（如“收款方”“-”）。规范化结果用于去重与展示。
- `note` 最大长度 500 字符。
- 交易被自动流程修改时，必须遵守 §11 的字段保护规则。

## 6. 状态机与可见性

状态迁移（唯一合法集合）：

```text
（无）      → PENDING      （自动决策不确定）
（无）      → CONFIRMED    （自动决策达标 / 手工记账保存 / Pending 编辑后入账）
PENDING    → CONFIRMED    （用户编辑后入账 / 用户未修改直接确认）
PENDING    → IGNORED      （用户忽略）
PENDING    → DUPLICATE    （用户判定“这是同一笔”）
PENDING    → DELETED      （用户删除）
CONFIRMED  → PENDING      （用户主动要求重新识别；不自动发生）
CONFIRMED  → DELETED      （用户删除）
CONFIRMED  → DUPLICATE    （用户判定重复）
IGNORED    → PENDING      （用户从日志恢复）
DELETED    → CONFIRMED    （30 天恢复窗口内恢复）
DUPLICATE  → PENDING      （用户撤销重复判定）
```

允许的操作可见性矩阵：

| 状态 | 列表可见 | 计入统计 | 可编辑字段 | 可删除 | 可恢复 | 可忽略 |
|---|---|---|---|---|---|---|
| PENDING | 仅 Pending 列表 | 否 | 是 | 是 | — | 是 |
| CONFIRMED | 是 | 是 | 是 | 是 | 30 天内 | 否 |
| IGNORED | 仅捕获日志 | 否 | 否 | 是（物理删除仅日志） | 是（恢复为 PENDING） | — |
| DELETED | 否 | 否 | 否 | — | 30 天内 | 否 |
| DUPLICATE | 仅捕获日志与重复详情 | 否 | 否 | 是 | 是（恢复为 PENDING） | 否 |

禁止：

- 任何未列出的状态迁移。
- 自动流程执行 `CONFIRMED → PENDING`（该迁移只能由用户主动触发）。
- 自动流程修改已进入 `DELETED` / `IGNORED` / `DUPLICATE` 的记录。

## 7. Category

```text
id
name
type            EXPENSE | INCOME
icon
sortOrder       Int，升序展示
enabled         Boolean
systemDefined   Boolean
createdAt
updatedAt
```

规则：

- 同一 `type` 下 `name` 唯一。
- 已被交易引用的分类只能禁用（`enabled = false`），不得物理删除。
- 禁用分类不再出现在选择列表，但历史交易展示不受影响。
- 收入分类与支出分类互不可用。

## 8. Account 与支付渠道

账户表示真正的资金账户：

```text
id
name              // 例如：现金、招商银行储蓄卡、微信零钱、支付宝余额
type              CASH | DEBIT_CARD | CREDIT_CARD | THIRD_PARTY
channel           ALIPAY | WECHAT | BANK | CASH | OTHER   // 支付渠道，可为空
last4             String?      // 卡号后四位，可为空
enabled           Boolean
sortOrder         Int
isDefault         Boolean
createdAt
updatedAt
```

区分规则（本节为 SSOT）：

- **账户（Account）**是资金归属，用于统计、余额与预算之外的资金视图。
- **支付渠道（channel）**是支付的发起渠道，是账户的一个属性，**不是独立对象**。
- UI 上“支付方式”统一指向账户（展示为账户名 + 渠道），不得再维护一套独立的 `methods` 列表。
- 从上游识别中得到的 `accountHint` 只作为推荐值；匹配不到账户时进入 Pending（reason = ACCOUNT_UNCERTAIN）。
- 账户禁用后不出现在选择列表；历史交易保留引用。
- 账户不得物理删除，只能禁用。
- `type = CREDIT_CARD` 的账户在 v0.1 不参与余额计算，仅作为标签。

## 9. Budget

```text
id
scope           TOTAL | CATEGORY
categoryId      String?    // scope = CATEGORY 时必填；scope = TOTAL 时必须为空
period          MONTH      // v0.1 仅月度
periodKey       String     // 形如 "2026-10"，标识具体月份
limitMinor      Long
enabled         Boolean
createdAt
updatedAt
```

规则：

- 总预算（`scope = TOTAL`）每个 `periodKey` 唯一；分类预算每个 `periodKey + categoryId` 唯一。
- 总预算与分类预算互相独立，不做叠加校验。
- 预算统计不能把 Transfer 当作消费。
- Pending 不占用预算额度。
- DELETED 交易回滚其预算占用。
- REFUND 释放对应分类与总额的已用额度（按退款发生月）。
- 超预算仅做视觉提示，不影响数据写入。

## 10. CaptureEvidence

用于解释“为什么形成这笔账”。

```text
id
captureId
captureSource
engineVersion
ruleId
confidence
matchedKeywords
rejectedKeywords
rawCaptureRef        // 原始捕获的引用或脱敏文本
capturedAt
```

规则：

- 证据与 Transaction 通过 `evidenceId` 关联，证据不随交易删除而删除（用户清空日志时才清理）。
- `rawCaptureRef` 中敏感字段必须按 `02` §20 的脱敏清单处理后方可落库与展示。
- 清空捕获日志只清理日志与证据，不影响 Transaction 与字段保护标记。

## 11. 用户修改保护（字段级）

保护粒度：**字段级**，不是记录级。

表示：

```text
FieldEdit
  transactionId
  fieldName        // merchant | amountMinor | type | categoryId | accountId
                   // | sourceAccountId | targetAccountId | transactionTime | note
  editedAt
  editedValueHash  // 可选，用于审计
```

规则：

- 用户实际修改过哪个字段，就只保护那个字段。
- 被保护的字段**永不被自动流程覆盖**，包括以下场景：上游重新识别、规则重新运行、去重合并、置信度回退、用户主动要求重新识别后的重跑。
- 若被保护字段后来被判定为不可靠，自动流程**不得清空或改写**；只能通过新增 Pending 建议（作为独立建议项展示）由用户决定。
- 用户**未修改任何字段**而直接点击“保存并入账”：只置 `confirmedByUser = true`，不产生任何 `FieldEdit`。
- `CONFIRMED → PENDING`（用户主动要求重新识别）后重新决策时，已存在的 `FieldEdit` 仍然生效，不得因重跑而清除。
- `FieldEdit` 必须参与备份（见 `02` §17），恢复时 Merge 模式不得用备份数据覆盖本地已保护的字段。

## 12. 去重规则（SSOT）

分两级：捕获级去抖与交易级判重。

### 12.1 捕获级去抖（不产生业务判重结论）

上游同一事件可能被重复投递。

- 同一 `packageName + notificationId + postTime` 视为同一事件，只保留一条捕获记录。
- 缺失 identity 字段时，按 `merchant` 与 `amountMinor` 相等且交易时间差的绝对值 ≤ 180 秒识别为疑似同一次投递；**仍不能确定时一律进入 Pending**，不得直接判定为重复。

说明：捕获级去抖只用于避免同一事件被处理两次，不产出 `DUPLICATE` 结论。

### 12.2 交易级判重（产出判重结论）

判定顺序：

1. `externalTransactionId` 精确相同 → Duplicate。
2. 渠道单号相同且捕获时间在 24 小时内 → Duplicate。
3. 语义兜底，以下条件**全部满足**才判定 Duplicate：
   - `amountMinor` 相等；
   - 两条记录的交易时间差的绝对值 ≤ **180 秒**；
   - 且满足其一：规范化后 `merchant` 相等，或（`direction` 相同且 `accountId` 相同）。

规则：

- 窗口语义统一为“交易时间差的绝对值 ≤ 180 秒”，不得实现为单侧 180 秒或 360 秒窗口。
- 任一条件缺失 → **不判定 Duplicate**，标记 `POSSIBLE_DUPLICATE` 并进入 Pending。
- 禁止以“merchant + amount”单独判定重复。
- 禁止跨 `direction` 判重（EXPENSE 与 REFUND 不得互相判重）。
- 去重比较对象：新候选 vs 最近 7 天内的 CONFIRMED / PENDING / DUPLICATE 交易。
- 用户判定“这是同一笔”时：新候选状态置 `DUPLICATE`，**保留候选与证据，不物理删除**，并记录 `DuplicateDecision`。
- 用户判定“这是两笔不同交易”时：候选继续走编辑入账流程。
- 无法判定且用户未处理时，记录永久停留在 Pending，不得自动消失。

## 13. 交易关系

退款：

```text
refund.type = REFUND
refund.relatedTransactionId = original.id
refund.orphan = (original 不存在或 original.state = DELETED)
```

- 允许部分退款：单笔退款金额 ≤ 原交易金额；累计退款金额 ≤ 原交易金额。
- 累计校验在写入前完成；超限不得自动入账，进入 Pending（reason = REFUND_UNCERTAIN）。
- 统计冲减口径见 `02` §14（按退款发生月冲减）。

转账：

```text
transfer.type = TRANSFER
transfer.sourceAccountId = 转出账户
transfer.targetAccountId = 转入账户
transfer.categoryId = null
```

- 转账为单条记录；两侧账户余额各变化一次。
- 转账不进入消费统计与预算。

## 14. 领域不变量

### 金额

- `amountMinor >= 0`
- 禁止 `Double` / `Float` 参与金额存储与最终运算

### 类型

- 必须是合法 `TransactionType`

### 状态

- 必须是合法 `TransactionState`
- 状态迁移必须属于 §6 的合法集合

### Confirmed

Confirmed 交易必须拥有足够的信息形成正式账务：`type`、`amountMinor`、`transactionTime`、`currency`、`accountId`（TRANSFER 除外，用两侧账户代替）。

### Pending

Pending 可以缺少：

- category
- account
- merchant
- direction

但必须记录 Pending 原因，且至少一个 reason 非空。

### User Edit

被 `FieldEdit` 标记的字段不得被任何自动流程覆盖。

### Transfer

Transfer 不进入普通消费统计，且 `categoryId` 必须为空。

### Refund

Refund 必须关联原交易或标记 `orphan`，且不得与原交易形成循环引用。

## 15. 领域服务边界

上游采集/识别模块不允许：

- 写账然数据库
- 访问 UI
- 直接创建或修改最终 Transaction
- 决定 Pending / Confirmed

Parser（无论位于上游还是 Adapter）不允许：

- 写数据库
- 访问 UI
- 直接创建最终 Transaction
- 修改用户已有交易

Dedup 不允许：

- 自行决定业务分类
- 修改原始捕获数据
- 覆盖用户受保护字段

Decision 是唯一允许决定 Pending / Confirmed / Duplicate / ClearlyInvalid 的环节。

UI 不允许：

- 自己实现重复判断
- 自己计算相似度或置信度
- 自己实现金额解析
- 自己修改数据库
- 展示 Domain 未提供的判断结论（例如相似度分数、时间差判定结果必须来自 Domain）

## 16. 领域决策规则（SSOT）

决策输入：规范化后的候选（含各字段 confidence 与 `overallConfidence`）、去重结果、字段保护状态。

决策输出：`CONFIRMED` / `PENDING(+reasons)` / `DUPLICATE` / `ClearlyInvalid`。

规则（按顺序短路，命中即终止；只有规则 1–10 全部不命中时才执行规则 11）：

1. `ClearlyInvalid`：无法获得任何可用字段（无金额且无方向且无任何文本线索），或来源包名不在支持列表内 → 不创建 Transaction，写 `CaptureLog`，状态 `IGNORED_INVALID`。
2. 关键字段校验：`amountMinor` 或 `direction` 缺失，或任一关键字段 confidence `< 0.5` → `PENDING`，reason 至少包含 `AMOUNT_UNCERTAIN` 或 `DIRECTION_UNCERTAIN`。
3. 整体阈值：`overallConfidence < 0.8`（阈值可配置，默认 `0.8`）→ `PENDING`，reason 至少包含 `LOW_CONFIDENCE`。
4. 去重结果为 Duplicate → `DUPLICATE`（保留候选与证据）。
5. 去重结果为 POSSIBLE_DUPLICATE → `PENDING`，reason 包含 `POSSIBLE_DUPLICATE`。
6. `currency != CNY` → `PENDING`，reason 包含 `AMOUNT_UNCERTAIN`。
7. 账户无法匹配 → `PENDING`，reason 包含 `ACCOUNT_UNCERTAIN`。
8. 分类无法确定 → `PENDING`，reason 包含 `CATEGORY_UNCERTAIN`（金额与方向明确时也进入 Pending，不允许猜分类入账）。
9. 商户无法确定（merchant 为空，或 `merchantConfidence < 0.5`）→ `PENDING`，reason 包含 `UNKNOWN_MERCHANT`。
10. 上游结果不可用（上游未识别、schema 校验失败、结果缺少可用字段但又不满足规则 1）→ `PENDING`，reason 包含 `UNSUPPORTED_NOTIFICATION`。
11. 上游类型未定义或语义不可信（借贷、还款、报销等，见 §18.2）→ `PENDING`，reason 包含 `DIRECTION_UNCERTAIN`。
12. 以上全部不命中 → `CONFIRMED`。

优先级说明：

- 规则 8 优先于规则 12：即使 `overallConfidence ≥ 0.8`，分类未确定也必须是 Pending，不得 Confirmed。
- 同一候选可能命中多条规则：全部 reason 都要落库（例如同时命中原因为 `CATEGORY_UNCERTAIN` 与 `LOW_CONFIDENCE`）。
- `CONFIRMED` 的充分必要条件：`overallConfidence ≥ 0.8` 且关键字段齐备且关键字段 confidence ≥ 0.5 且规则 4–11 均不命中。
- 规则 2 与规则 3 是前置条件而非互斥分支：不满足时直接 Pending，因此规则 12 的判定不受二者影响。

约束：

- 决策是**唯一**决定状态的地方；Adapter、Normalize、Confidence、Dedup、Repository、UI 都不得决定状态。
- 决策必须记录原因集合，供 Pending 页面与捕获日志展示。
- 决策不得覆盖被保护字段：若候选值与被保护字段冲突，保留用户值，并将冲突记入证据。
- 字段级 confidence 不足（非关键字段，如 `categoryConfidence` / `accountConfidence` / `merchantConfidence`）不单独产生“字段级 Pending”状态，而是通过对应 reason（`CATEGORY_UNCERTAIN` / `ACCOUNT_UNCERTAIN` / `UNKNOWN_MERCHANT`）使**整笔记录**进入 Pending，由用户在 PendingEdit 中修正该字段后入账。

## 17. 单一事实来源

每类数据必须存在唯一修改入口：

- Transaction → Transaction Repository / Domain
- Category → Category Repository
- Account → Account Repository
- Budget → Budget Repository
- FieldEdit → Domain（用户编辑时写入）
- CaptureLog / CaptureEvidence → Capture 适配层写入，UI 只读
- UI State → ViewModel / StateHolder

约束：

- 同一业务对象不得存在两个编辑入口（例如分类只在分类页编辑，规则只在规则页编辑）。
- 同一业务结论不得在两个层分别计算（状态由 Decision 决定，去重结论由 Dedup 产出，UI 只展示）。

## 18. 上游输入映射（AutoAccounting）

上游宿主接入协议见 `07` §3.5。本节定义**唯一允许的映射口径**；实现不得自行扩展映射。

### 18.1 字段映射（上游 `BillInfoModel` → 账然）

| 上游字段 | 类型 | 账然对应 | 强制处理 |
|---|---|---|---|
| `id` | `Long` | `externalId`（证据保留） | 不得作为账然主键 |
| `type` | `BillType` | `TransactionType` | 按 §18.2，未列出的取值一律 Pending |
| `money` | `Double` | `amountMinor: Long` | `BigDecimal(money.toString())` 一次转分；禁止用 `*100` 或 Double 运算（`AGENTS.md` §5、§4） |
| `fee` | `Double` | 手续费 / 优惠（写入证据） | `< 0` 手续费、`> 0` 优惠；**不得修改原 `money`**（上游实现有就地改写先例） |
| `currency` | `String`（含 code/rate） | `currency` | v0.1 仅 CNY；**丢弃 `rate`，禁止换算**；非 CNY → Pending |
| `time` | `Long`（毫秒） | `transactionTime` + `transactionTimeZone` | 上游无时区信息，须由账然补齐；禁止用省略时区的本地格式化字符串落库 |
| `shopName` / `shopItem` | `String` | `merchant` / `note` | `merchant` 按 §5 规范化 |
| `cateName` | `String` | `categoryHint` | 上游含父子分隔符，需拆分；映射不到 → `CATEGORY_UNCERTAIN` |
| `accountNameFrom` / `accountNameTo` | `String` | `sourceAccountId` / `targetAccountId` | 上游给的是**名称**，须 Name→ID 映射；映射不到 → `ACCOUNT_UNCERTAIN` |
| `bookName` | `String` | — | 账然单账本，忽略 |
| `groupId` | `Long` | — | 上游自己的短时同额合并，**不得当作 `DUPLICATE` 结论**（与 §12 分级不同） |
| `channel` / `app` | `String` | `source` + 证据 | 按 `07` §5 映射到 `CaptureSource`，不得新增枚举值 |
| `state` | `BillState` | — | 上游状态机（`Wait2Edit` 等），**不得映射为 `TransactionState`** |
| `extendData` / `tags` / `flag` / `remark` | `String` | `note` / 证据 | 原样入证据，脱敏后落库 |

### 18.2 上游 `BillType` → 账然 `TransactionType`

| 上游 `BillType` | 账然映射 | 附加条件 |
|---|---|---|
| `Expend` | `EXPENSE` | — |
| `Income` | `INCOME` | — |
| `Transfer` | `TRANSFER` | `accountNameTo` 非空且两侧账户都能映射；否则 Pending（`TRANSFER_UNCERTAIN`），`categoryId` 必须为空 |
| `IncomeRefund` | `REFUND` | 必须能关联原交易；无法关联 → Pending（`REFUND_UNCERTAIN`） |
| `ExpendReimbursement` / `IncomeReimbursement` | **不映射 → Pending** | 报销 ≠ 退款，语义未定义（`DIRECTION_UNCERTAIN`） |
| `ExpendLending` / `ExpendRepayment` / `IncomeLending` / `IncomeRepayment` | **不映射 → Pending** | 借贷 / 还款语义未定义（`DIRECTION_UNCERTAIN`） |
| 其他未列出取值 | **不映射 → Pending** | 一律 `UNSUPPORTED_NOTIFICATION` |

原则：**上游未定义的类型绝不猜测映射**（`AGENTS.md` §1）。新增映射必须先按 `review/DEVELOPMENT_PLAN.md` §7 的变更流程改本节，再改代码。

### 18.3 置信度

上游不输出置信度，由 Adapter 按字段缺失情况推导各字段 confidence 与 `overallConfidence`，再交 §16 决策；推导规则必须可测试，不得随手给固定值。
