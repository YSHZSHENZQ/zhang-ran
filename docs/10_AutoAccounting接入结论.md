- 上游代码位置与行号会随上游升级失效；**行号仅作快速定位提示**，实现必须以固定 commit 的实际代码为准。

## 2. 可行性结论（M0）

| 问题 | 结论 |
|---|---|
| 上游事件能否被第三方宿主接收 | **能**。唯一出站通道是隐式 `Intent(ACTION_VIEW, 自定义scheme://…)`；四个既有宿主（钱迹 / 一羽 / 一木 / 小星）写法一致 |
| 是否存在 AIDL / ContentProvider / 广播回执 | **没有**。全仓唯一 provider 是 `FileProvider` 与 `ShizukuProvider`，无业务 provider |
| 上游自带 HTTP 服务能否跨应用取数 | **不能**。服务端仅放行 loopback（`127.0.0.1` / `::1`），跨应用被拒 |
| 不打补丁能否打通 | **不能**。宿主适配器列表是**硬编码** `listOf(...)`，无 SPI / 反射 / 配置文件扩展点 |
| 上游是否要求宿主实现接口 | **不要求**。要求的是上游侧新增一个实现 `IAppAdapter` 的适配器类 |
| 无 Root 的 OCR 模式能否作为降级路径 | **能采集，但结果更差**。该模式下上游会裁剪能力（标签 / 多币种）并显著放慢同步节流 → 缺失字段一律 Pending |

核心约束：**能力在宿主侧，注册权在上游侧**（协议不对称）。

## 3. 方案选择

| 方案 | 做法 | 结论 |
|---|---|---|
| A 受控上游补丁 | fork 上游 → 新增适配器 → 注册一行 → 版本锚定 | **采用**（`07` §2.1 已定义边界） |
| B 伪装已支持宿主 | 账然注册钱迹等 scheme，让用户选“钱迹” | 不采用：语义错误、无回执、参数受限、用户困惑 |
| C 完全不改上游 | 用上游“仅自动记账”模式另寻通道 | **不可行**：该模式只标记已同步、不向任何外部应用发数据；读库 / HTTP / 导出均无可用通道 |

方案 C 的四种通道逐一证伪：私有目录无法读、HTTP 仅 loopback、导出只支持外部 HTTPS 端点、自建采集违反 `07` §1。

## 4. 宿主接入契约（v1）

契约内容与约束以 `07` §3.5 为准，本节只记录**上游侧事实**：

| 事实 | 说明 |
|---|---|
| 出站方式 | `Intent(Intent.ACTION_VIEW, uri)` + `FLAG_ACTIVITY_NEW_TASK` |
| 拉起方式 | 上游用 `startActivityIfResolvable(...)` → **找不到宿主时静默失败**，不报错 |
| 回执 | 仅 Xposed 模式可拿到“写库成功”回执；非 Xposed 只能“拉起成功即标记”。v0.1 不做回执（`07` §3.5） |
| 适配器接口成员 | `pkg`、`link`、`icon`、`desc`、`name`、`supportSyncAssets()`、`features()`、`syncAssets()`、`syncWaitBills()`、`syncBill()`、`sleep()` |
| 注册点 | `AppAdapterManager` 的硬编码列表；补丁在此追加一行 |
| 节流 | `sleep()` 由宿主实现；有宿主在 OCR 模式使用 3000ms 级节流，需评估账单积压 |
| 副作用 | 上游对象可能被**就地修改**（有适配器直接把手续费写回 `money`）→ 账然必须只读投影，禁止复用或回写 |
| Xposed 作用域 | 上游只 Hook 白名单内包名；v0.1 账然不进作用域（仅 URI 接收） |

## 5. 上游输出模型关键事实

字段名与映射口径以 `03` §18.1 为准，本节记录**必须在实现中防范的上游事实**：

| 事实 | 影响 |
|---|---|
| `money` / `fee` 是 `Double` | 必须 `BigDecimal(money.toString())` 转分；禁止 `*100` 或 Double 运算 |
| `fee` 语义随类型变化 | 支出：优惠 `total = money + fee`；还款 / 转账：手续费 `total = money - fee`、优惠 `total = money + fee` → **不得无条件把 `fee` 当同类项处理** |
| `time` 无时区 | 上游格式化用设备默认时区；账然必须自行补 `transactionTimeZone` |
| `groupId` 是上游的“短时同额合并去重 id” | **不得**当作账然的 `DUPLICATE` 结论（分级不同，`03` §12） |
| `cateName` 是名称 | 模型层的父子拆分与各宿主出站格式的写法**并不一致**（上游转换层存在多种分隔写法）→ 具体分隔符必须在 P0 用真实载荷确认，禁止按文档猜测 |
| `accountNameFrom` / `accountNameTo` 是**名称** | 账然需 Name→ID 映射；映射不到 → Pending |
| `state`（`Wait2Edit` / `Synced` 等）是上游状态机 | **不得**映射为账然 `TransactionState` |
| `extendData` 承载报销 / 销账关联 | v0.1 报销类一律 Pending，不解析其关联 |
| `currency` 含 `rate` | v0.1 仅 CNY，丢弃 `rate`，禁止换算 |
| `auto` / `ruleName` / `tags` / `flag` / `rawAccountName*` | 只作证据，不参与账然领域判断 |

## 6. 上游自带能力与账然边界

上游自身已声明并使用：通知监听（NLS）、无障碍、短信接收、前台服务、`INTERNET`、`QUERY_ALL_PACKAGES`、BugSnag 遥测、云更新与许可校验、本地 Ktor 服务、AI 提供方、汇率（数据源为第三方记账应用接口）、WebView + JS 规则引擎、悬浮窗、手势注入、DEX 反射。

账然边界（细节见 `07` §9.1、`04` §9.2）：

- 上述能力**全部属于上游**，账然不申请、不重建、不复用其 UI / Room / AI / 规则引擎。
- 账然自身 Manifest 不得出现采集类权限与 `INTERNET`。
- 上游库文件与账然库文件完全隔离；上游**不得**作为账然的库依赖引入（仅运行时共存）。
- 账然只消费上游经宿主契约交出的结果。

## 7. v0.1 明确不做（与上游相关）

`07` §1 前提之外，本文件额外确认：

| 项 | 结论 |
|---|---|
| 回执 / 反向 Hook | 不做（不进上游 Xposed 作用域、不 Hook 账然、不确认对方是否真的入账） |
| 复用上游 UI / Room / AI / 规则引擎 / 导出 | 不做 |
| 上游结果直接生成 `CONFIRMED` | 禁止（必须走账然 Decision） |
| “仅自动记账”模式取数 | 已证伪，不做（`07` §2.1 之外的替代通道不存在） |
| 借贷 / 还款 / 报销类入账 | 一律 Pending（`03` §18.2） |
| 多币种换算 | 不做（非 CNY → Pending） |

## 8. 待确认（进入实现前用真实载荷回答）

以下问题**不能靠文档推断**，必须在打通阶段（上游补丁 + 账然只打日志）用真实载荷确认，确认结果回写本文件与 `03` §18：

1. `cateName` 在宿主契约载荷中的实际父子分隔写法。
2. `fee` 在各 `BillType` 下的实际符号与组合。
3. `app` / `channel` 的实际取值集合与其到 `CaptureSource` 的完整映射（不得新增枚举值）。
4. 同一账单是否存在重复投递（需要 `notification identity` 级别的去抖依据）。
5. OCR 模式下缺失字段的实际集合（决定 Pending reason 分布）。

## 9. 上游升级时必须复核的点

按 `07` §22 升级流程，其中第 2、8 步对应本节：

1. 适配器接口 `IAppAdapter` 是否有成员变化（新增 / 删除 / 语义变化）。
2. 宿主注册点是否仍为硬编码列表（若已提供扩展点 → 删除补丁）。
3. 出站方式是否仍是隐式 Intent + scheme。
4. `BillInfoModel` 字段是否有增删或类型变化（尤其 `money` / `fee` / `time` / `state` / `groupId`）。
5. §5 的“关键事实”是否仍成立。
6. 本文件 §1 的版本锚点与 §8 的确认结果同步更新。
