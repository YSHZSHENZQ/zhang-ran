# 10 AutoAccounting 接入结论

版本：v0.1  
定位：本文件是**采集核心接入侧的结论性记录与硬事实清单**，供实现与验收直接引用。本文件部分结论基于**双 APK（宿主 + 外部插件）**前提；该前提已由**单 APK（账然内嵌采集核心）**取代，相关章节见下标注。

规则：

- 本文件只记录**结论、契约与约束**，不重复业务规则（业务见 `02`/`03`，接入规则见 `07`）。
- 上游代码位置与行号会随上游升级失效；**行号仅作快速定位提示**，实现必须以固定 commit 的实际代码为准。
- 上游升级后必须按 `07` §22 重跑验证，并同步更新本文件的版本锚点与结论。
- 本文件是**结论级**记录。需要逐步执行的工程方案（里程碑、任务书、验收命令等）属于本地指导材料，**不在本仓库内，也不得被引用**（见 `AGENTS.md` §11.1）。

## 2. 可行性结论（M0）

> **前提变更说明**：本节结论产生于双 APK（宿主 + 外部插件）时期。单 APK 方案下"能否被宿主接收""不打补丁能否打通"等问题**不再适用**（采集核心直接内嵌、进程内调用）；下表保留原结论供追溯，并在"新前提下的结论"列给出替代。

| 问题 | 原结论（双 APK） | 新前提下的结论（单 APK） |
|---|---|---|
| 上游事件能否被第三方宿主接收 | **能**。唯一出站通道是隐式 `Intent(ACTION_VIEW, 自定义scheme://…)`；四个既有宿主（钱迹 / 一羽 / 一木 / 小星）写法一致 | **不再适用**：采集核心**内嵌并可进程内直接调用**，不经 Intent / scheme（`07` §3.5） |
| 是否存在 AIDL / ContentProvider / 广播回执 | **没有**。全仓唯一 provider 是 `FileProvider` 与 `ShizukuProvider`，无业务 provider | 保留（同进程内不需要 IPC） |
| 上游自带 HTTP 服务能否跨应用取数 | **不能**。服务端仅放行 loopback（`127.0.0.1` / `::1`），跨应用被拒 | **改为**：本机回环**可用**，账然 APK 因此声明 `INTERNET`（D1） |
| 不打补丁能否打通 | **不能**。宿主适配器列表是**硬编码** `listOf(...)`，无 SPI / 反射 / 配置文件扩展点 | **作废**（不再需要补丁；整包内嵌，见 `07` §2.1） |
| 上游是否要求宿主实现接口 | **不要求**。要求的是上游侧新增一个实现 `IAppAdapter` 的适配器类 | **作废**（无宿主关系） |
| 无 Root 的 OCR 模式能否作为降级路径 | **能采集，但结果更差**。该模式下上游会裁剪能力（标签 / 多币种）并显著放慢同步节流 → 缺失字段一律 Pending | **保留**（仍适用） |

原核心约束"**能力在宿主侧，注册权在上游侧**（协议不对称）"**已随宿主关系消失**：单 APK 下采集能力与领域决策位于**同一 APK 内**，边界由 Gradle 模块与进程内接口约束（`07` §3.5）。

## 3. 方案选择

> 原 A/B/C 三方案（受控补丁 / 伪装宿主 / 完全不改上游）均基于双 APK 前提，**已作废**。单 APK 下的方案对比：

| 方案 | 做法 | 结论 |
|---|---|---|
| 整包内嵌 | 上游 `:app` 整体降为 library，连同其 UI 一起编译进账然 APK | **本期采用**（D2 / D6-a），UI 瘦身后置 |
| 抽取采集模块 | 只抽出采集与识别相关类，剥离 UI / Hook | 后置（D6-c，可选） |
| 分步落地 | D6-a 降 library 编译通过 → D6-b 剥离 Xposed 身份 → D6-c 拆 `:capture` | **采用此节奏**（`07` §21） |

## 4. 内嵌接口事实

> **原"宿主接入契约（v1）"整节作废**（URI scheme / Intent 契约随宿主关系消失）。接口定义已改为**进程内接口**，契约内容以 `07` §3.5 为准；本节只保留在新方案下**仍然成立**的上游侧事实。

| 事实 | 在新方案下的状态 |
|---|---|
| 出站方式（`Intent(ACTION_VIEW, uri)` + `FLAG_ACTIVITY_NEW_TASK`） | **作废**：改为进程内调用 |
| 拉起方式（`startActivityIfResolvable` 静默失败） | **作废**：同进程无"找不到接收方"情形 |
| 适配器接口成员（`pkg`/`link`/`icon`/`desc`/`name`/`supportSyncAssets()`/`features()`/`syncAssets()`/`syncWaitBills()`/`syncBill()`/`sleep()`） | **保留为事实**：内嵌后仍可复用其 `IAppAdapter` 体系；升级复核见 §9 |
| 注册点（`AppAdapterManager` 硬编码列表） | **保留为事实**：内嵌后可直接在模块内修改，不再需要补丁 |
| 节流（`sleep()`，OCR 模式可能 3000ms 级） | **保留**：内嵌后仍需评估账单积压（`07` §19 健康度） |
| 副作用（上游对象可能被**就地修改**，如把手续费写回 `money`） | **保留且更需防范**：必须只读投影，禁止复用或回写 |
| Xposed 作用域（只 Hook 白名单包名） | **保留为事实**；内嵌后 Xposed 身份被剥离（D6-b），该模式不支持（`07` §8） |

## 5. 上游输出模型关键事实

字段名与映射口径以 `03` §18.1 为准，本节记录**必须在实现中防范的上游事实**：

| 事实 | 影响 |
|---|---|
| `money` / `fee` 是 `Double` | 必须 `BigDecimal(money.toString())` 转分；禁止 `*100` 或 Double 运算 |
| `fee` 语义随类型变化 | 支出：优惠 `total = money + fee`；还款 / 转账：手续费 `total = money - fee`、优惠 `total = money + fee` → **不得无条件把 `fee` 当同类项处理** |
| `time` 无时区 | 上游格式化用设备默认时区；账然必须自行补 `transactionTimeZone` |
| `groupId` 是上游的“短时同额合并去重 id” | **不得**当作账然的 `DUPLICATE` 结论（分级不同，`03` §12） |
| `cateName` 是名称 | 模型层的父子拆分与各宿主出站格式的写法**并不一致**（上游转换层存在多种分隔写法）→ 具体分隔符必须在 P0 用真实载荷确认，禁止按文档猜测 |
| `accountNameFrom` / `accountNameTo` 是**名称** | 账然需 Name→ID 映射；映射不到 → Pending |
| `state`（`Wait2Edit` / `Synced` 等）是上游状态机 | **不得**映射为账然 `TransactionState` |
| `extendData` 承载报销 / 销账关联 | v0.1 报销类一律 Pending，不解析其关联 |
| `currency` 含 `rate` | v0.1 仅 CNY，丢弃 `rate`，禁止换算 |
| `auto` / `ruleName` / `tags` / `flag` / `rawAccountName*` | 只作证据，不参与账然领域判断 |

## 6. 采集核心自带能力与账然边界

采集核心自身已声明并使用：通知监听（NLS）、无障碍、短信接收、前台服务、`INTERNET`、`QUERY_ALL_PACKAGES`、BugSnag 遥测、云更新与许可校验、本地 Ktor 服务、AI 提供方、汇率（数据源为第三方记账应用接口）、WebView + JS 规则引擎、悬浮窗、手势注入、DEX 反射。

单 APK 下账然边界（细节见 `07` §9、`04` §9.2）：

- 上述能力的**声明全部落在账然 APK 自身**（内嵌后不再有"上游独立应用"，见 `07` §9 权限矩阵）；其中 `INTERNET` 仅用于与本机识别服务的回环通信（D1）。
- 采集核心**作为 Gradle 模块内嵌**于账然 APK（D6）；其 UI 仅在悬浮窗 / 记账面板这一处出现（D3-边界，`07` §16）。
- **两套 Room 库文件必须隔离**（D4）：库文件名不同、互不 import、互不查询；备份只覆盖账然账务数据（`02` §17）。
- 采集核心**不得持有账然 Repository / DAO 引用**，不得直接写 `transactions`、不得决定 Pending / Confirmed（`07` §3.5）。
- 账然只消费采集核心经**进程内接口**交出的结果。

## 7. v0.1 明确不做（与上游相关）

`07` §1 前提之外，本文件额外确认：

| 项 | 结论 |
|---|---|
| 回执 / 反向 Hook | 不做（不进上游 Xposed 作用域、不 Hook 账然、不确认对方是否真的入账） |
| 复用上游 UI / Room / AI / 规则引擎 / 导出 | 不做（采集核心 UI 仅作悬浮窗 / 记账面板入口，D3-边界） |
| 上游结果直接生成 `CONFIRMED` | 禁止（必须走账然 Decision） |
| 借贷 / 还款 / 报销类入账 | 一律 Pending（`03` §18.2） |
| 多币种换算 | 不做（非 CNY → Pending） |

## 8. 待确认（进入实现前用真实载荷回答）

以下问题**不能靠文档推断**，必须在打通阶段（上游补丁 + 账然只打日志）用真实载荷确认，确认结果回写本文件与 `03` §18：

1. `cateName` 在宿主契约载荷中的实际父子分隔写法。
2. `fee` 在各 `BillType` 下的实际符号与组合。
3. `app` / `channel` 的实际取值集合与其到 `CaptureSource` 的完整映射（不得新增枚举值）。
4. 同一账单是否存在重复投递（需要 `notification identity` 级别的去抖依据）。
5. OCR 模式下缺失字段的实际集合（决定 Pending reason 分布）。

## 9. 上游升级时必须复核的点

按 `07` §22（采集核心版本合并）流程，本节列出必须复核的点：

1. `BillInfoModel` 字段是否有增删或类型变化（尤其 `money` / `fee` / `time` / `state` / `groupId`）。
2. 内嵌模块的 Gradle 依赖与**身份声明**是否变化（如 Xposed 入口、权限声明、`minSdk`、第三方库）。
3. `IAppAdapter` 体系是否仍有成员变化（若内嵌后不再使用，可整块剥离，见 D6-c）。
4. §5 的“关键事实”是否仍成立。
5. 本文件 §1 的版本锚点与 §8 的确认结果同步更新。
