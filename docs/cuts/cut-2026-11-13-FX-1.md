- Owner 导出日志（PM 已读）只有两条 `SERVICE_CONNECTED`（2026-11-12 13:10、13:31），这笔 ¥25.10 没有任何记录。

代码（`f08dada6` / 当前 `dev` 同树）核对：

1. **读错窗口（本刀主因）。** `AccessibilityCaptureService.scheduleSample` 在延迟 300ms 后读 `rootInActiveWindow`（`AccessibilityCaptureService.kt:77`，延迟 `DelayedSampleScheduler.kt:54`），再把**事件包名**写进快照（`NodeTreeReader.kt:91`），不核对根节点实际属于哪个包，也不按 `event.source` / `getWindows()` 找与事件包名匹配的窗口。服务配置只有 `flagReportViewIds`，没有 `flagRetrieveInteractiveWindows`（`accessibility_service_config.xml:11`）。
2. **拒绝原因不可导出。** `NOT_PAYMENT_PAGE` / `WINDOW_NULL` / `NODE_EMPTY` / `SWITCH_OFF` 只走 `AccessibilityDiagnostics.log` → `Log.d`（tag `ZhangRanAccessibility`，`AccessibilityDiagnostics.kt:13,30-34`；写出点 `AccessibilityCaptureService.kt:85-120`）。`shouldForward` 等于 `parse() != null`（`AccessibilitySnapshotParser.kt:99`），门槛失败进不了 ingest，因而进不了 `capture_logs`、导出 JSON 也看不到。只有 `SERVICE_CONNECTED`（`AccessibilityConnectivityRecorder.kt:40-56`）和解析通过后的落库结果会进导出日志。
3. **金额规则仍是这页的真实风险，但不是这次漏记的已证原因。** 「支付成功」节点自己不带金额时，整页必须恰好解析出一个不同的金额，否则 `parse` 返回 null（`AccessibilitySnapshotParser.kt:117-124`）。`amountOf` 只认带 `¥`/`￥` 的串，或带小数的 `x.xx元`（同文件 92-94、176-181）；单独的 `25.10` 节点不算金额。优惠券若写成 `¥10` 会把金额数撑破；截图上的整数「10元 / 2元 / 12元」按当前正则**不会**被算作金额。若主金额是完整的 `¥25.10` 且与「订单金额 ¥25.10」相同，金额门槛其实能过。这次快照里根本没有结果页，所以不是金额门槛把这笔丢掉的。
4. **无商户页可能被写成错误商户。** `merchantRaw` 可以为空（同文件 19、129；已有单测「找不到商户时留空」）。但 `fieldLabels` 没有「订单金额」「交易方式」（54-79 行），`merchantOf` 最后会取第一个未被拒绝的文本（194 行），这页会把商户写成「订单金额」。
5. **14:45「疑似失效」与 24 小时无成功捕获一致，待写进日志。** `AutoLedgerHealth.resolve` 用 `lastCaptureAtMillis ?: watchStartedAtMillis`，满 24 小时且开关开、无障碍已授权 →「疑似失效」（`AutoLedgerHealth.kt:31,37-39`）。`lastCaptureAt` 只在 ingest 成功写库后更新（`AccessibilitySnapshotIngest.kt:235,279` → `health.recordCapture`）；拒绝采样和 `SERVICE_CONNECTED` 都不算。09:00 仍是「可用」、14:45 变成「疑似失效」，与「这台真机从未成功落过一笔 + 距打开总开关可能已满 24 小时」相符。这不是服务已死的直接证据，但当前导出日志无法向用户解释这次翻转。
