# 09 总结经验教训

用途：记录**已发生的关键问题**与**已验证的解决对策**，避免重复踩坑。
写入规则：

- **只加不改**：新问题追加到末尾，不修改、不删除已有条目。
- **只记关键且重要的问题**：会阻塞工作、会导致数据/文件损坏、会反复出现的问题；小问题不记。
- **最简短直白**：一条问题 = 一行“问题” + 一行“对策”，不写背景、不写推理、不写代码示例。
- 追加时沿用现有编号，不重排。

## 1. 工作区 Windows 权限（DSH 沙箱）

**问题**：pwsh 任何命令都失败：`SetNamedSecurityInfoW failed (Win32 5): grantWrite(<工作区>)`；连 `Get-Location` 都跑不了。
**对策**：用 repair 脚本修一次（`-Path` 与 `-AllowRoot` 都填工作区根目录），跑完再重试原命令。

**问题**：ACL 看起来完全正确（有 FullControl、WRITE_DAC/WRITE_OWNER 都有），但 pwsh 只能在**工作区根目录**建/写文件，在 `docs/` 等子目录一律 `Access denied`。
**对策**：根因是**强制完整性标签**缺失（根目录带 Low，子目录没有→Medium 挡住低完整性进程），不是 ACL，别再跑 ACL 脚本。改用 write/edit 工具写子目录文件，或把会话切到 full access。

**问题**：日志里出现 `\BaseNamedObjects\msys-2.0S5-…: 0xC0000022`，`git ls-remote`/`git push` 报 `Could not read from remote repository`。
**对策**：是 Git 自带的 MSYS `ssh.exe` 在沙箱下崩溃。改用 Windows OpenSSH：`git config core.sshCommand C:/Windows/System32/OpenSSH/ssh.exe`（用正斜杠），密钥仍用 `~/.ssh/id_ed25519`。

## 2. 文件操作

**问题**：探针命令 `"x" | Set-Content <真实文件>` 不报错却把该文件内容清空成 1 行（“Access denied 只在真正写入时才抛，而且文件已被截断”）。
**对策**：**永远不要**用 `Set-Content` 打真实文件做写入测试；测权限只用 `New-Item -ItemType File` 建新文件，再用 `Remove-Item` 删掉。

**问题**：`Get-Item`/`FileInfo.Length` 在刚被改动或正被读取的文件上会返回过期的假大小（例如真实 99 KB 显示 1 B），据此判断“文件损坏”会误判。
**对策**：核实文件以 `read` 工具的实际内容为准；需要大小时重开一次 pwsh 再 `Get-ChildItem`。

**问题**：`robocopy` 在沙箱内对不可写目标会默认重试一百万次并挂死（120 s 后仍在跑）。
**对策**：不要在沙箱内用 robocopy 做移动/复制；用工具层操作。必须用时至少加 `/R:0 /W:0`。

## 3. 文档与 Git 流程

**问题**：同一事实分散写在多份文档里，改一处后其他文档旧值仍在（例如金额单位、章节号、页面数量不一致）。
**对策**：每条规则只在一处定义（SSOT），其他文档只写“见 X §N”；改规则时按报告的“连带影响”列一起改。

**问题**：引用章节号（`见 03 §16`）在文档重排后失效，Agent 会读到错误章节。
**对策**：改章节顺序后必须全库复查 `§` 引用；引用优先写“章节标题”而非纯数字。

**问题**：在文档中间**插入**一个小节，会把它之后所有小节号推后一位，其他文档引用全部错位。
**对策**：优先把新内容挂到已有小节下（如 §X.1），避免整体重排；确需插入时必须同步更新被推后章节的全部外部引用。

## 4. Android 构建工具链

**问题**：AGP 9.0 起内建 Kotlin，再应用 `org.jetbrains.kotlin.android` 会直接失败并提示该插件已不需要。
**对策**：AGP 9+ 不要应用 KGP 插件；Compose 编译器插件仍单独应用（版本与 AGP 匹配）；`kotlin { compilerOptions { jvmTarget } }` 仍可用。

**问题**：Hilt 的 Gradle 插件在配置期用 `Class.forName` 探测 KSP 任务类，探测不到就报“KSP plugin was detected... task class could not be found”（Dagger issue #3965）；旧 Hilt（2.52）与 KSP 2.3.x 必然冲突，且与插件声明 scope 无关。
**对策**：升级 Hilt（2.60.1 已验证可用）并让 KSP 与 Hilt 在同一 scope 应用；`hilt.enableAggregatingTask` 是**项目属性**（须 `-P` 传入），写进 `gradle.properties` 无效。

**问题**：AndroidX/Compose 新构件要求依赖方 `compileSdk` 更高，报 “requires ... to compile against version 37 or later”。
**对策**：先按提示提高 `compileSdk`（`targetSdk` 可不动）；若本机缺平台，`sdkmanager` 的包名可能带小数点（如 `platforms;android-37.2`），不要写成 `platforms;android-37`。

**问题**：`compose-ui-tooling` / `profileinstaller` 会给合并 Manifest 带入 `android:exported="true"` 的组件，违反“零导出组件”类红线。
**对策**：在 `src/debug/AndroidManifest.xml` 用 `tools:node="remove"` 移除对应组件，不要用 `dependenciesInfo.includeInApk=false`（会导致 APK 缺少依赖元数据而无法安装）。

**问题**：清理工作区时把整个 `gradle/` 目录删掉，连带误删了还没提交的版本目录与 wrapper（无 git 历史可恢复）。
**对策**：删除目录前先列出其内容并确认无自有文件；`gradle/wrapper/gradle-wrapper.jar` 这类二进制可从同版本来源复制，版本目录必须重建。

**问题**：只在 `build.gradle.kts` 用 `java { toolchain }` 声明 JDK 21，构建期 JVM 仍是 JDK 17 时，`hiltJavaCompileDebug` 报 `release 21 不受支持`——Hilt 生成的 Java 编译任务**不跟随 toolchain**。
**对策**：构建期 JVM 必须满足目标 Java 版本（本项目为 JDK 21+）；toolchain 声明保留用于 IDE 解析与报错，但不能替代构建期 JVM。

**问题**：在 `gradle.properties` 写 `org.gradle.java.home` 指向本机某个 JDK，换机器或 CI 直接失败；而删掉它又可能让构建期 JVM 版本不足。
**对策**：不要硬编码本机 JDK 路径；改为要求环境提供合规 `JAVA_HOME`（或 CI 配置对应 JDK），并把这一前置写进工程 README。

**问题**：版本目录里保留已不再使用的插件条目（如 AGP 9 下的 `kotlin-android`），后续任务容易误以为它仍应被应用。
**对策**：构建方式变更后核对「catalog 的 `[plugins]` 条目 ↔ 构建脚本实际引用」是否一一对应，无用条目直接删除并在注释里写明原因。

## 5. 真机（小米 / HyperOS）测试

**问题**：小米设备拒绝 ADB 安装：`INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`（系统日志 `MIUILOG- assertCallerAndPackage … Install canceled by user`）。streamed / `--no-streaming` / push 后 `pm install` / `--user 0` 四种方式全部失败，且安装期间屏幕无任何弹窗可点，`settings put` 相关开关也无效。
**对策**：这是设备侧安全策略（HyperOS 的「USB 安装」开关，需要登录小米账号并在开发者选项中授权）。**无法用技术绕过**；必须由人在设备上开启，或改用其它设备/模拟器。

**问题**：`ui-test-manifest` 配成 `androidTestImplementation` 时，Compose 测试宿主 `androidx.activity.ComponentActivity` 会落到测试 APK 进程，报 `Intent in process X resolved to different process X.test`；若该声明完全缺失，测试会在“取 Activity”阶段永久阻塞（无任何测试日志、AM 从不启动 Activity）。
**对策**：`ui-test-manifest` 必须配 `debugImplementation`（进目标 App 的 debug 变体）；改动后先检查合并 Manifest 里是否确有 `androidx.activity.ComponentActivity`，再跑真机测试。

**问题**：在同一个测试方法里循环调用多次 `composeRule.setContent` 会永久挂起（Compose 测试只允许一次 `setContent`）。
**对策**：用 `@RunWith(Parameterized::class)` 一个用例测一个页面；并给每个用例加 `Timeout` 规则，避免“挂死而不是失败”。

**问题**：用 `waitUntil` 轮询替代 Compose 标准断言后，用例连启动都做不到（在测试线程轮询会阻塞主线程推进组合）。
**对策**：保留标准断言（`onNodeWithText(...).assertIsDisplayed()`），只用 `Timeout` 兜底；不要自造同步机制。

**问题**：kill 掉 Gradle 后台任务后，设备上的 `am instrument` 不会随之结束，会一直占着包（实测残留 10 分钟以上），让后续 run 卡在安装/启动阶段。
**对策**：每次真机测试前先 `am force-stop <包名>`，并用 `ps -A | grep app_process` 确认为空再开始。

**问题**：判断“真机测试是否在运行”时，只看 Gradle 的 `Running tests on devices` 会误判（它可能只是启动了会话，用例一个都没跑）。
**对策**：用设备侧三证据判断：`ps` 里进程的 `ETIME`、`logcat` 的 `TestRunner: started/finished/failed`、`logcat -b events` 的 `am_activity`/`START u0`。

**问题**：真机被人工占用（正在用其它 App、有触摸事件）时，instrumentation 会把测试宿主 Activity 拉不起来，表现为每个用例都 `TestTimedOutException: test timed out after 60 seconds`。
**对策**：跑真机测试前确认设备空闲（前台为桌面、无触摸）；并关闭动画缩放（`window/transition/animator_duration_scale` 置 0）。

**问题**：小米 / HyperOS 真机受安装策略限制时，`connectedDebugAndroidTest` 完全无法进行（连装包都失败），排查会浪费大量时间。
**对策**：验证阶段优先用本机 AVD（`Medium_Phone_API_36` 已验证 36 个用例全绿）；真机只用于最终确认，且先确认能 `adb install` 成功再跑测试。

**问题**：`.gitignore` 里写不带前导斜杠的目录名（如 `AutoAccounting/`）会匹配**任意层级**同名目录；本例误伤了包目录 `com/zhangran/app/autoaccounting/`，且被忽略的文件在 `git status` 里连 `??` 都不显示，导致**静默漏提交**（T1b 的一个包说明文件就这样丢过一次）。
**对策**：只忽略仓库根的目标时一律加前导斜杠（`/AutoAccounting/`）；每次交付后用 `git status --ignored=matching` 复核对新增文件是否被意外忽略。
