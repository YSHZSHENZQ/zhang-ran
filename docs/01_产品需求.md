# 01 产品需求

版本：v0.1  
产品：账然  
状态：基线文档

## 1. 产品定位

账然是一款 Android 本地优先的个人记账应用。

核心能力不是“手工记账”，而是：

> 用户完成支付后，应用尽可能自动识别支付信息并形成账务记录；无法可靠识别时交给用户确认。

### 1.1 能力边界（v0.1 已定前提）

v0.1 **采集层复用 AutoAccounting 的模块化核心**，账然不另行自建采集实现；该核心以 **Gradle 模块内嵌于账然 APK**（单 APK 交付，见 `07` §21 的 D6）。

| 能力 | 归属 | 说明 |
|---|---|---|
| 捕获（Hook / 通知 / 无障碍 / OCR / 短信） | 内嵌采集核心（AutoAccounting，Gradle 模块） | 按工作模式提供；账然不重复实现 |
| 规则匹配、识别、证据 | 内嵌采集核心 | 输出原始识别结果与证据 |
| 采集接入与适配（`capture/`、`autoaccounting/`） | 账然 | 接收**内嵌采集核心**的结果、屏蔽其模型、转换为统一候选 |
| 领域模型、领域决策、Pending/Confirmed、统计、预算、备份、用户修改保护 | 账然 | 唯一有权决定账务结果的层 |
| 产品 UI | 账然 | 采集核心 UI 仅作悬浮窗 / 记账面板入口（`07` §16） |

边界约束：内嵌采集核心不得直接写入账然的 Room / Transaction；账然不得把账务决策下放给采集核心。

### 1.2 使用边界（自用，不分发）

- 本项目当前定位为**个人本地自用**：不上架应用商店、不对外分发、不商业化。
- 内嵌采集核心声明 GPL-3.0；内嵌后账然为 GPL-3.0 衍生作品，在“仅自用、不再分发”前提下不触发分发义务。
- 纪律：**记录采集核心来源与 commit**、**保留其 LICENSE 与版权声明**、仅自用不分发。
- 若未来要分发或商业化，必须先重新做许可证合规评估，或重做采集层。详见 `07_自动记账与AutoAccounting集成.md` §20。

## 2. 目标用户

主要面向：

- 经常使用微信、支付宝支付的个人用户
- 希望减少手工记账操作的人
- 重视本地数据和隐私的人
- 接受必要时人工确认的人

## 3. 核心问题

传统记账主要依赖：

1. 用户主动打开记账应用。
2. 手工填写金额。
3. 手工选择分类。
4. 手工选择账户。

这导致：

- 操作成本高
- 容易忘记
- 账务记录不连续
- 长期坚持困难

账然希望把记账变成：

> 支付发生 → 自动捕获 → 自动识别 → 自动入账 / 待确认。

## 4. 产品目标

### G1 自动记录

尽可能自动识别微信、支付宝等支付产生的交易。

### G2 正确性

自动识别的正确性高于自动化率。

### G3 可解释

用户应该能够知道：

- 这笔账为什么被记录
- 来源是什么
- 使用了什么规则
- 识别置信度如何

### G4 可修正

用户可以修改：

- 商户
- 金额
- 类型
- 分类
- 账户
- 时间
- 备注

### G5 可恢复

用户可以备份和恢复自己的账务数据。

### G6 隐私

核心账务功能不依赖云端。

## 5. MVP 范围

### 必须支持

- 手工记账
- 账单列表
- 交易详情
- 分类
- 账户
- 月度统计
- 预算
- 待确认
- 自动记账状态
- 捕获日志
- 数据备份 / 恢复
- 搜索
- 微信 / 支付宝自动识别能力的接入基础（复用上游 AutoAccounting 模块化核心）
- 重复交易检测
- 转账
- 退款
- 用户修改保护

### 可以在 MVP 后实现

以下能力均由内嵌采集核心按工作模式提供，账然侧只做接入适配，不在 v0.1 自建：

- 无障碍兜底（Accessibility fallback）
- OCR
- AI / VLM
- Xposed / LSPosed Hook 模式
- 短信渠道

其余 MVP 后能力：

- 商户自动学习
- 更复杂的规则编辑器
- 多设备同步
- 云端服务

## 6. 非目标

MVP 不做：

- 云端账号体系
- 云端保存全部账务
- 社交
- 多人家庭账本
- 投资组合管理
- 银行级财务管理
- 强制 AI
- 依赖网络才能记账
- 自建第二套采集实现（采集与识别统一来自内嵌采集核心）
- 上架应用商店、对外分发、商业化（当前为个人自用）

## 7. 产品原则

### 7.1 本地优先

账务数据默认在本机保存。

### 7.2 自动化服从正确性

不确定：

`Pending > 自动入账`

### 7.3 用户拥有最终决定权

自动识别只是建议。

### 7.4 过程可解释

自动生成的账务需要保留必要的来源和识别证据。

### 7.5 可恢复

数据结构和备份格式必须具有版本信息。

## 8. 成功标准

用户完成一次微信 / 支付宝支付后：

1. 应用能够捕获有效账务信息。
2. 系统能够识别交易方向。
3. 能够提取金额。
4. 能够识别商户。
5. 能够确定或推荐分类。
6. 能够检测重复。
7. 达到领域决策阈值（默认 `overallConfidence ≥ 0.8` 且关键字段充分）进入 Confirmed。
8. 不确定进入 Pending。
9. 用户可以修改并确认。
10. 最终账务不会因为后续自动识别而被覆盖。

## 9. 关键用户体验

用户不应该需要理解：

- Parser
- Candidate
- Adapter
- Rule Engine
- Dedup

这些是内部实现。

用户看到的应该是：

- 自动记账
- 待确认
- 识别来源
- 为什么需要确认
- 修改后入账

## 10. 版本范围

v0.1 主要确定：

- 产品边界
- 核心用户流程
- 数据安全原则
- 自动记账基本流程
- 采集与识别能力的来源与使用边界（内嵌采集核心、个人自用、GPL-3.0）
- UI 信息架构

不在 v0.1 中锁死所有具体实现细节；但 `02`/`03` 中的金额单位、领域决策规则、去重规则、退款口径、转账表达、用户修改保护粒度属于已冻结规则，实现必须遵守。
