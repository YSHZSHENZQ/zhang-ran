## 1. 总体结论

**NOT_READY（阻塞项集中为 4 类：采集层前提、金额单位、领域决策与模型表达、备份恢复语义；其余问题可并行开工）**

原因（不是“文档不够详细”，而是“文档之间指向不同的实现，且核心账务规则缺失”）：

1. **采集层的已定前提没有进入任何文档，且现有文本与之冲突。** 项目方已确定“采集层复用 AutoAccounting 的模块化核心，仅自用、不分发”；但 8 份文档中没有任何一句声明该前提，且 `04 §9`、`07 §8`、`02 §19` 原型引导页都把采集写成账然自建 `NotificationListenerService`。这决定宿主接入、权限矩阵、`CaptureSource` 映射、Parser 归属与排期，是最高优先级阻塞项。
2. **金额单位存在 100 倍歧义。** `02` 中 `¥100 → amountMinor=10000`，`03` 中 `¥12.34 -> 1234`。按 `02` 的示例比例，`03` 的 `1234` 代表 1234 元。两者都能自证，Agent 必须猜。猜错即账务金额错误。（复核确认为全报告唯一“猜错即错账且不可逆”的问题。）
3. **自动记账的核心决策逻辑没有权威归属。** “谁决定 Pending / Confirmed”“置信度阈值是多少”“解析（Parser）属于账然还是上游”在 02/03/04/07 之间存在三种不同的 pipeline 画法与职责划分，且全文没有任何置信度阈值。
4. **领域模型无法表达已声明的 MVP 功能。** `Transfer` 的 `sourceAccount / targetAccount` 不在 `Transaction` 字段清单中；`Refund` 的冲减统计口径全文未定义；`Budget` 无 `period` 语义、无总预算概念（原型与 02 都有月度总预算）。
5. **用户修改保护只有一句原则，没有可实现的语义。** 02 §5 与 03 §11 在“用户改过的字段不得被覆盖”这一层并不矛盾；真实缺陷是 03 §5 只给出了 `editedByUser` 一个名字、**粒度与类型未定**，且 03 §11 明说“或者字段级”，即文档把实现选择留白。
6. **统计、预算、备份恢复的验收标准不可执行。** `08` 只有勾选项（“Stats 正确”“Budget 正确”），没有可验证的输入输出；`02` 的统计口径全部写作“默认建议”。
7. **UI 规格与原型存在缺页、重名、口径不一致。** 原型有 `onboard`（权限引导）页面但 06 无规格；06 无 `支付方式` 字段但原型详情页有且可编辑；原型详情页存在一个“编辑交易（金额/商户/备注）”弹窗，正是 AGENTS.md 第 7 条明令避免的“字段可点击 + 另一个编辑入口”。

因此：**修订前的状态下不应开始正式开发。** 不是“修好措辞即可”，而是至少需要先解决第 2 节 P0 中的采集层前提、金额单位、决策规则与模型表达。

> **修订后状态（对应 §14）**：以上 P0 条目均已按第 14 节的 8 项冻结决策写入 `01`–`08` 与 `README`，采集层前提已落定，字段级 SSOT、状态机、决策规则、去重规则、备份恢复语义与逐条验收判据均已补齐。因此本报告的结论从 **NOT_READY** 变更为 **READY_WITH_FIXES**：可立即开工 §14.2 的 5 个并行动作；§14.4 的 8 项确认与 §4.1 的 P2 项不阻塞开工，但需在对应功能进入实现前确认。

### 9.4 主要操作与编辑方式（重点：字段可点击 + 重复编辑按钮）

**发现重复编辑入口风险（AGENTS.md §7 / 06 §8 明令避免）**

1. 原型详情页存在 `editHandlers.detail`：一个“编辑交易”弹窗，可同时改“金额 / 商户名称 / 备注”，而这三个字段在详情页本身也是可点击编辑的（备注卡片 `data-edit="detailNote"`）。这是“字段可点击 + 另一个编辑入口”的典型形态。该弹窗在原型脚本中没有任何 UI 触发点（属死代码），但文件里存在就无法保证 Agent 不照抄。
2. 原型分类管理页：分类项本身可点击编辑（`data-edit="cat-*"`），编辑弹窗内又是同一套字段，且弹窗内额外提供“删除分类”。同一对象的编辑入口为 1 处 + 弹窗内动作，尚可接受，但 02 §9“不得物理删除已被引用的分类”与弹窗“删除分类”冲突（修订后 06 §4.12 已禁止物理删除）。
3. 原型分类管理页内嵌“自动分类规则”（可编辑、可添加），与规则页（同样“添加”+ 可编辑）构成同一业务对象的两个入口（修订后 06 §4.12 已禁止，规则只在 RulesScreen 编辑）。
4. 原型预算页：总预算卡片整体可点（`data-edit="totalBudget"`，卡片内又有“点击修改”文字），分类预算行整体可点；这与 02 §12“点击预算卡片修改 / 点击分类预算行直接修改，不需要额外顶部编辑按钮”一致，无重复按钮问题。
5. 原型添加/编辑类入口统一使用“添加”（`addCategoryBudget` / `addCategory` / `addRule` / `addAccount`），符合 06 §8“新增使用添加”。
6. 原型详情页“删除记录”为独立明确按钮，符合 02 §10。

**其他操作一致性问题**

- 06 §4.7 的 PendingScreen 操作写“编辑后入账 / 查看重复 / 忽略”，原型同一列表三行的按钮实际不同（“编辑后入账”+“忽略”，“查看重复”+“忽略”，“编辑后入账”+“忽略”），未说明是“按 Pending 原因决定动作集”还是行级差异。
- 06 §4.8 的 PendingEditScreen 底部为“保存并入账”，原型一致；但原型类型选项含“转账/退款”，分类只在 Pending 编辑场景给 4 项（无收入分类），账户只有 3 项，与手工记账页字段不一致。
- 原型的“记一笔”页签底部有完整数字键盘与“保存”，保存后直接回首页并只弹 Toast；06 §4.3 只说“保存后 → Confirmed”，未定义保存后的导航行为（返回首页？保留表单？）。

### 9.5 Dialog / BottomSheet

- 05 §13 Dialog 适用：自定义分类、删除确认、重复判断、恢复模式选择、高风险操作。原型中存在：自定义分类、删除交易、删除分类/账户/规则/备份、清空数据、清空日志、恢复方式选择、测试自动记账、原始捕获——其中“测试自动记账”与“查看原始捕获”属信息展示型弹窗，05 §13 未列；06 §4.10/§4.6 也未定义这两者的呈现方式。
- 05 §14 BottomSheet 适用：分类选择、账户选择、筛选、快速操作。原型把“分类选择”“账户选择”“时间选择”全部实现为底部弹窗式 `modal-overlay`，与 05 §13 的 Dialog 清单有交叉（分类选择同时可被理解为 Dialog 与 BottomSheet），06 未指定每个选择器用 Dialog 还是 BottomSheet。

## 10. 自动记账边界检查

逐层检查职责是否唯一（输入、输出、失败处理、是否允许进入下一阶段、最终决定权）。

| 层 | 输入 | 输出 | 责任方（文档声明） | 能否失败 / 失败后 | 职责是否唯一 |
|---|---|---|---|---|---|
| Capture | 系统通知事件 | `NotificationEnvelope` | 04 §9（NotificationListenerService）、07 §3（AutoAccounting / Capture Engine） | 未定义（仅 07 §17 一句“Capture Log + 可重试/Pending”） | **否**（账然 Service 与 AutoAccounting 都可产出，边界未定） |
| Parse | `NotificationEnvelope` | `ParseResult`（03）或 `TransactionCandidate`（07 §4） | 03 §3（账然 Parser）、07 §3（AutoAccounting 负责 Rule matching / AI recognition） | 未定义（部分解析/无法解析的输出表示与后续态未定） | **否**（两套 parse 归属，输出类型不一致） |
| Candidate | 解析结果 / 外部识别结果 | `TransactionCandidate` | 03 §4、04 §2、07 §6 | 允许字段不完整（03 §4） | **部分**（来源有两处，但对象定义唯一） |
| Normalize | 候选 | 规范化候选 | 04 §5（Domain） | 未定义（规范化失败、冲突字段如何处理均无） | **否**（只有职责名，无规则、无输入输出契约） |
| Confidence | 规范化候选 | 各字段 confidence + overall | 07 §13（给出字段清单）、04 §5（Domain） | 未定义（阈值缺失，见 P0-3） | **否**（阈值、算法、判定接口全无） |
| Dedup | 候选 + 已有 Transaction | `DuplicateDecision` / 继续 | 03 §12、04 §5、07 §14（账然负责） | 未定义（不能判定时是 Pending 还是继续入账未定） | **部分**（归属唯一，判定条件缺失；02 §6 又把最终决定交给用户） |
| Pending / Confirmed | 去重结果 + 置信度 | 状态决定 | 02 §3（流程图）、04 §5（Domain 负责 Pending 决策）、07 §3（账然 Domain 负责 Pending/Confirmed） | 未定义 | **否**（决策点位置与阈值均无权威定义 → ABV-1） |
| Transaction | 状态决定 + 数据 | 落库交易 | 03 §5、04 §6 | 未定义（写库失败、约束冲突的处理无） | **是**（唯一入口清晰） |

危险项检查结论：

- **Parser 直接写数据库**：03 §15、04 §20 明文禁止 → 无越界定义风险（文档层面已禁止）。
- **AutoAccounting 直接创建 Transaction**：07 §2 明文禁止 → 无越界定义风险。
- **AI 直接创建 Transaction**：04 §12、07 §11 明文禁止 → 无越界定义风险。
- **UI 自己判断 Duplicate**：03 §15 禁止，但 02 §6“用户最终选择”与 06 §4.8 的页面操作，使“用户判定”与“UI 判定”的边界不清 → 存在 ARCHITECTURE_BOUNDARY_VIOLATION 风险（ABV-4）。
- **UI 自己计算 Confidence**：03 §15 禁止，但 `06 §4.6/§4.7` 要求展示 confidence 与 Pending 原因，且原型 `待确认` 页面展示置信度百分比来源不明 → 需明确“展示”与“计算”的分界。
- **多个模块同时决定 Pending / Confirmed**：**已实际存在**。02 §3、04 §5、07 §3/§7 三处都可被读成决策发生地 → 违反风险最高，属 P0-3。

## 13. 最终需要人工确认的问题

仅列出必须由产品负责人 / 用户本人决定、Agent 不应自行决定的问题。

**Q1（金额单位，阻塞）** `amountMinor` 是否恒为“货币最小单位（分）”，即 ¥100 = `10000`、¥12.34 = `1234`？`02 §1` 的示例需要如何更正？

**Q2（Pending/Confirmed 决策权与阈值，阻塞）** 谁拥有唯一决策权（Domain？），置信度阈值取多少、是否可配置、低于阈值时是按字段进入 Pending 还是整笔进入 Pending？

**Q3（Transfer 模型，阻塞）** 转账用“一条 Transaction + source/target 账户字段”表达，还是“两条腿 + 关联 id”？转账是否影响账户余额展示？手工记账是否必须支持创建转账？

**Q4（Refund 会计口径，阻塞）** 退款如何冲减消费？按退款发生月冲减，还是回溯原交易月份？部分退款是否允许？退款是否影响预算？退款对象被删除后如何处理？

**Q5（用户修改保护粒度，阻塞）** 采用字段级保护还是记录级 `editedByUser`？用户在 Pending 页“未做任何修改直接保存并入账”是否算用户修改？被用户修改过的字段若后续识别不可靠，是否允许回退为 Pending？

**Q6（Ignore 语义，阻塞）** “系统判定无效”与“用户忽略”是否是两个不同概念？系统 Ignore 是否必须留下可查看记录？用户忽略后能否恢复？

**Q7（Budget 模型与行为，阻塞）** 是否支持“月度总预算 + 分类预算”两级？超预算是否只做视觉提示？退款、删除交易、Pending 是否影响预算占用？预算周期是否仅月度？

**Q8（备份内容与恢复语义）** 备份是否包含 Pending、捕获证据、重复决定、日志？Merge 模式遇到同一记录的冲突以谁为准？Replace 是否会清空未备份内容？Settings Only 具体包含哪些设置？

**Q9（MVP 捕获实现主体）** v0.1 是否由账然自己用 `NotificationListenerService` 完成微信/支付宝捕获，AutoAccounting 仅作为后续可选识别源？若必须集成 AutoAccounting，MVP 是否接受 GPL-3.0 带来的分发约束？

**Q10（隐私与网络）** MVP 是否声明“不申请 INTERNET 权限”？若是，原型“关于”页的“检查更新 / GitHub 仓库 / 反馈与建议”入口是否删除？“AI 默认关闭”的开启入口是否出现在 MVP 中？

**Q11（去重判定条件）** 去重的时间窗口取值？semantic fallback 允许的条件组合（是否必须有 account 或 source 参与）？用户选择“这是同一笔”之后，被判定为重复的新候选是丢弃、合并入原记录还是永久留痕？

**Q12（搜索行为）** “金额”检索是等值还是区间？“日期”是否只支持范围选择？结果默认排序？是否需要分页？

**Q13（Delete / IGNORED 的恢复窗口）** 删除是软删除并可恢复（多久？），还是“删除后无法恢复”（原型文案）？IGNORED 是否可在列表中重新激活？

**Q14（“其他”分类语义）** 在“其他”上输入自定义名称后：是创建一个新的持久分类，还是仅本笔交易使用自由文本？该行为是否也适用于 Pending 编辑页和收入分类？

**Q15（页面范围与命名）** “我的（Settings）”页是否纳入 v0.1 规格？权限引导页（onboard）是否属于 v0.1？底部导航是否固定为五项？

**Q16（原型的效力边界）** 原型中的示例数字、`zhangran_*.db` 备份名、支付方式/账户双列表、`已超支 ¥20`、`118 笔自动入账` 等，是否统一视为“不可作为行为与数据依据的视觉占位”？（建议在 06 §7 补一条显式声明。）
