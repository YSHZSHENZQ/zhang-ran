# 02 产品规格

版本：v0.1  
说明：本文件的数值与行为规则为已冻结规格。其中涉及领域对象、金额单位、决策与去重的权威定义见 `03_领域模型与业务规则.md`，本文件不重复定义，只做引用与产品行为约束。

## 1. 核心交易类型

系统必须区分：

- EXPENSE：支出
- INCOME：收入
- TRANSFER：转账
- REFUND：退款

金额始终保存绝对值。

单位：`amountMinor` 恒为**货币最小单位**（人民币为“分”），权威定义见 `03` §4。

例如：

- 支出 ¥100 → `EXPENSE + amountMinor=10000`
- 收入 ¥100 → `INCOME + amountMinor=10000`
- 支出 ¥12.34 → `EXPENSE + amountMinor=1234`

不要使用负数表达交易方向。

手工记账入口的产品范围：

- “记一笔”页支持创建 EXPENSE / INCOME。
- 转账可通过手工记账入口创建（类型选择含“转账”），必须选择转出账户与转入账户。
- 退款可通过“退款”入口创建，并通过 `relatedTransactionId` 关联原交易；无法关联时进入 Pending（见 §7）。

## 2. 交易状态

### PENDING

需要用户确认。未进入正式统计。

### CONFIRMED

已经确认并进入正常账务。

### IGNORED

**用户动作**：用户明确忽略该候选/记录。

- 必须保留原始捕获证据与忽略原因。
- 用户可从捕获日志中查看，并可将 IGNORED 恢复为 PENDING 重新处理。
- 不计入正式统计。

### DELETED

用户删除。

- 采用软删除（墓碑）语义，保留 `deletedAt`。
- 删除不代表物理立即删除；备份与恢复必须保证一致性。
- 不计入正式统计。
- 恢复窗口为 30 天；超过窗口后是否物理清理由后续版本决定，v0.1 不做物理清理。

### 系统判定无效（不是状态，不产生 Transaction）

系统判定“明确无效”（例如完全无法解析的通知）**不创建任何 Transaction**，而是写入捕获日志：

- 日志状态：`IGNORED_INVALID`
- 必须保留原始捕获证据，用户可在捕获日志中查看。
- 该记录永远不出现在账单列表中，也不计入任何统计。

注意：`IGNORED`（用户动作）与“系统判定无效”（日志记录）是两个不同概念，不得混用同一字段表达。

## 3. 自动记账决策

流程：

```text
捕获（内嵌采集核心）
 ↓
解析 / 识别（内嵌采集核心）
 ↓
账然 Adapter：转换为候选 + 证据
 ↓
规范化 Normalize
 ↓
置信度 Confidence
 ↓
去重 Dedup
 ↓
领域决策 Decision（唯一决策点）
 ├─ 关键字段齐备 + 各关键字段 confidence ≥ 0.5 + overallConfidence ≥ 阈值
 │  + 无任何阻断性 reason（分类/账户/商户未定、疑似重复、非 CNY 等）→ Confirmed
 ├─ 命中任一阻断条件 → Pending（带 reason 集合）
 ├─ 判重为重复 → Duplicate（保留候选与证据）
 └─ 明确无效 → 不产生 Transaction，写捕获日志 IGNORED_INVALID
```

权威定义：

- 决策唯一发生在**领域决策环节（Decision）**，位于 Dedup 之后、Repository 之前；其他层不得决定 Pending / Confirmed。详见 `03` §16。
- 置信度阈值默认 `0.8`，可配置；关键字段（amount、direction）缺失或置信度 `< 0.5` 时整笔 Pending。详见 `03` §16。
- `03` §16 的规则按顺序短路：只要命中任一阻断性 reason（例如分类无法确定），即使 `overallConfidence ≥ 阈值` 也必须进入 Pending。

## 4. Pending 原因

至少支持：

- UNKNOWN_MERCHANT
- AMOUNT_UNCERTAIN
- DIRECTION_UNCERTAIN
- CATEGORY_UNCERTAIN
- ACCOUNT_UNCERTAIN
- POSSIBLE_DUPLICATE
- REFUND_UNCERTAIN
- TRANSFER_UNCERTAIN
- UNSUPPORTED_NOTIFICATION（上游未识别或识别结果不可用）
- LOW_CONFIDENCE

规则：

- 一笔记录可以同时存在多个 reason，界面必须至少展示严重度最高的一个。
- Pending 页面必须让用户知道“为什么需要确认”，并与 reason 一一对应。

## 5. Pending 操作

用户可以：

- 编辑
- 编辑后入账
- 查看重复（仅当存在 POSSIBLE_DUPLICATE 时出现）
- 忽略
- 查看原始捕获信息

操作集按 reason 决定：

| reason | 可用操作 |
|---|---|
| POSSIBLE_DUPLICATE | 查看重复 / 忽略 |
| 其他所有 reason | 编辑后入账 / 忽略 |

“编辑后入账”：

1. 用户修改字段。
2. 保存修改。
3. 将结果作为最终交易，状态变为 CONFIRMED。
4. **仅将用户实际修改过的字段**标记为受保护（字段级，见 `03` §11）。
5. 用户未修改任何字段而直接点击“保存并入账”时：只置 `confirmedByUser = true`，不标记任何字段受保护。
6. 后续自动识别不得覆盖已标记受保护的字段。

## 6. 重复交易

系统必须提供专门的重复判断流程，且去重判定遵循三级规则（权威定义见 `03` §12）：

1. `externalTransactionId` 精确相同 → 判定 Duplicate。
2. 渠道单号相同且捕获时间在 24 小时内 → 判定 Duplicate。
3. 语义兜底（全部满足才判定）：
   - `amountMinor` 相等；
   - 两条记录交易时间差的绝对值 ≤ **180 秒**；
   - 且满足以下之一：商户名规范化后相等，或（交易方向相同且账户相同）。

任一条件缺失 → **不判定 Duplicate**，标记 `POSSIBLE_DUPLICATE` 并进入 Pending。

比较范围：新候选只与**最近 7 天内**的 CONFIRMED / PENDING / DUPLICATE 交易比较；超出范围的旧记录不参与判重。

另外，上游同一事件可能重复投递，账然在捕获阶段先做去抖（同一 `packageName + notificationId + postTime` 只保留一条）；捕获级去抖不产生判重结论，缺 identity 且无法确定时一律进入 Pending。

用户最终选择：

- **这是同一笔**：新候选标记为 `DUPLICATE`，保留证据与用户决定记录，不物理删除。
- **这是两笔不同交易**：进入编辑流程，确认后作为独立交易入账。

禁止：以“商户 + 金额”单独判定重复。

## 7. 退款

退款独立成一条记录，`type = REFUND`，通过 `relatedTransactionId` 指向原交易。

规则：

- 默认 **按退款发生月冲减当月消费**，不做回溯重算历史月份。
- 允许部分退款；单笔退款金额 ≤ 原交易金额，累计退款金额 ≤ 原交易金额。
- 退款不计入预算占用，并释放对应分类的已用额度。
- 原交易被删除（DELETED）时，退款记录保留并标记 `orphan = true`，同时进入 Pending 提示用户处理。
- 无法确定原交易时进入 Pending（reason = REFUND_UNCERTAIN）。

## 8. 转账

转账不能作为普通消费统计。

必须关联：

- source account（转出账户）
- target account（转入账户）

规则：

- 转账为**单条** `Transaction`（`type = TRANSFER`），`sourceAccountId` 与 `targetAccountId` 必填且不得相同。
- `type = TRANSFER` 时不得设置 `categoryId`。
- 转账进入账户余额流水（两侧账户余额各变化一次），但不进入消费统计与预算占用。
- 转账不计入“本月支出 / 本月收入 / 本月结余”。

## 9. 分类

分类必须支持：

- 系统分类
- 用户自定义分类
- 启用 / 禁用
- 排序

规则：

- `type` 取值为 EXPENSE / INCOME，支出分类与收入分类分开管理，互相不可混用。
- 已经被交易引用的分类不得物理删除，只能禁用（DISABLED）。
- 禁用分类：不出现在新建与编辑的选择列表中；历史交易仍正常显示该分类名称。
- 分类重名不允许（同一 `type` 下名称唯一）。

### “其他”分类

手工记账中选择“其他”时：

1. 打开“自定义分类”弹窗。
2. 用户输入分类名称。
3. 确认后在当前 `type` 下创建（或复用同名）该分类，本笔交易使用该分类。
4. 支出与收入均适用，分别归入对应 `type`。
5. 在 Pending 编辑页选择“其他”时使用同一规则与同一弹窗。

## 10. 编辑规则

交易详情页：

- 普通字段直接点击编辑，字段范围：商户、金额、类型、分类、账户、时间、备注。
- 不再提供重复的顶部“编辑”按钮。
- 不再提供重复的底部“修改分类”按钮。
- 不再提供“编辑交易”这类一次修改多个字段的聚合弹窗（否则与字段级编辑构成双入口）。
- 保留明确的“删除记录”操作，并需要二次确认。
- 删除确认文案必须与软删除语义一致（提供恢复窗口说明），不得写“删除后无法恢复”。

## 11. 首页

首页核心展示：

- 本月支出
- 本月收入
- 本月结余
- 最近交易
- 待确认数量（含 POSSIBLE_DUPLICATE，不重复计数）
- 自动记账状态

规则：

- “BALANCE”语义统一为“本月结余”，格式统一为 `¥ 1,234.56`。
- 本月结余 = 本月收入 − 本月支出（不含转账；退款按 §14 口径冲减支出）。
- 首页不再展示未定义的“RECORDS / 记账笔数”指标，除非与统计页使用同一口径并显式命名。

## 12. 预算

预算支持两种范围（`scope`）：

- TOTAL：月度总预算
- CATEGORY：分类预算

交互：

- 点击预算卡片修改月度总预算
- 点击分类预算行直接修改该分类预算
- 不需要额外的顶部“编辑”按钮
- 支持添加分类预算

规则：

- `period = MONTH`，v0.1 仅支持月度。
- 总预算与分类预算互相独立，不做叠加校验。
- 超预算仅做视觉提示（文案 + 颜色），不阻止记账、不弹强制提示。
- Pending 不占用预算。
- DELETED 交易回滚其预算占用。
- REFUND 释放对应分类的已用额度。
- 转账不计入任何预算。

## 13. 搜索

至少支持：

- 商户
- 备注
- 金额
- 日期
- 分类
- 账户
- 类型
- 来源
- 状态

规则：

- 商户 / 备注：包含匹配（不区分大小写）。
- 金额：支持等值与区间两种方式。
- 日期：范围选择（起止日期）。
- 默认排序：交易时间倒序。
- 结果分页：每页 50 条，滚动加载。
- 筛选 chips 与上述维度对应关系为：全部（无筛选）、分类、类型、账户；chips 是维度的快捷入口，不是独立维度。

## 14. 统计

统计口径（已冻结，不再使用“默认建议”）：

- Pending：不计入正式统计。
- Confirmed：计入。
- IGNORED：不计入。
- DELETED：不计入。
- 系统判定无效：不产生交易，不计入。
- Transfer：不计入消费统计与收支统计；计入账户余额流水。
- Refund：冲减**退款发生月**的消费统计，冲减对象为对应分类与总额。

定义：

- 当月消费 = 当月 EXPENSE 合计 − 当月 REFUND 合计（同一分类内冲减；分类不明确时冲减总额）。
- 当月收入 = 当月 INCOME 合计。
- 当月结余 = 当月收入 − 当月消费。
- 趋势图与分类占比均使用上述口径，不含 Pending / IGNORED / DELETED / TRANSFER。

## 15. 自动记账设置

设置页（“我的”）至少提供：

- 自动记账总开关
- 权限状态（按工作模式显示，见 §19）
- 微信 / 支付宝捕获状态
- 测试自动记账
- 捕获日志入口
- 记账提醒（成功记录时是否通知）
- 暗色主题

页面归属：

- 自动记账总开关、权限状态、总状态入口放在“我的”页。
- 微信 / 支付宝状态、测试自动记账、捕获日志、解析规则放在“自动记账”页。
- 两页不得重复提供同一个开关。

## 16. 解析规则

规则需要具备：

- ruleId
- priority
- include keywords
- exclude keywords
- matchMode（匹配方式：`EXACT` / `CONTAINS` / `REGEX`，默认 `CONTAINS`）
- direction
- engineVersion（上游引擎的规则/版本标识，见 `07` §13）
- matched keywords（**每次匹配的结果，写入 `03` §10 的 CaptureEvidence，不是规则配置**）
- rejected keywords（同上）

匹配语义：

- 匹配方式支持 exact / contains / regex（默认 contains）；`matchMode` 是**规则级**属性，作用于该规则的 `include` 与 `exclude` 全部关键词。
- 匹配不区分大小写，全角与半角视为等价。
- `direction` 取值域为 EXPENSE / INCOME / TRANSFER / REFUND 或“未指定”。
- **priority 数值越小优先级越高**；多规则命中时按 priority 升序取第一条命中规则，并将其余命中规则记入证据（matchedRuleId 取生效规则的 ruleId）。
- 启用规则之间的 `priority` **必须唯一**；`priority` 并列时无判定依据，创建 / 编辑规则时必须拒绝重复值。
- include 命中且 exclude 未命中才算规则命中。
- 被 include 命中但被 exclude 拒绝的关键词必须写入 `rejectedKeywords` 证据。
- `include` / `exclude` 的存储形态为 **JSON 数组字符串（canonical）**，例如 `["付款成功","支付成功"]`：
  - 列类型 `TEXT`、`NOT NULL`；空集合存 `[]`，**不得**用 `null` 表示空（与"无效规则"无法区分）。
  - 序列化必须 **canonical 且稳定**：UTF-8、无多余空白、保持插入顺序、不转义非 ASCII（中文直接写出）。
    解析后再序列化必须逐字节相同，否则每次保存都会产生"假更新"。
  - 顺序无语义（匹配为"任一命中"）；解析时**去重并保留首次出现的顺序**；忽略纯空字符串项，`[""]` 归一为 `[]`。
  - 每项**保留原样、不做 trim**：大小写与全半角等价由匹配层负责（见上），避免存储层与匹配层重复规范化。
  - **解析失败不得静默当作空集合**（否则规则会变成"匹配一切"）：该规则视为不可用、不参与匹配，并记录日志。
  - `matchMode` 的存储形态：枚举名 `EXACT` / `CONTAINS` / `REGEX`，`TEXT`、`NOT NULL`、默认 `CONTAINS`。

规则测试：

- 输入一条捕获数据，展示命中规则、匹配关键词、被拒绝关键词与解析出的字段。
- 规则测试可临时使用**未保存**的规则；一旦保存规则，测试结果必须落库到捕获日志（状态 `RULE_TEST`）。

规则对象数量：

- v0.1 只有**一个**规则对象（解析规则），分类页内不得再提供第二套“自动分类规则”编辑入口；分类页只能跳转到规则页。

## 17. 备份

备份采用应用定义格式，而不是直接复制 Room 数据库。

- 备份**只覆盖账然账务数据**；内嵌采集核心自身的数据库（两套 Room 库文件隔离，见 `07` §9）**不参与备份**。

示例：

```text
zhangran-backup-v1-<yyyymmdd>.zip
├── manifest.json
├── transactions.json
├── categories.json
├── accounts.json
├── budgets.json
├── rules.json
├── pending.json
├── evidence.json
├── duplicate_decisions.json
├── capture_logs.json
├── field_edits.json
└── settings.json
```

内容范围：

- 必须包含：transactions、categories、accounts、budgets、rules、settings。
- 必须包含：pending、evidence、duplicate_decisions、capture_logs、field_edits（否则恢复会丢失 Pending 与证据，违反可解释性要求）。
- 不得包含：原始 OCR 截图、完整通知原文中的敏感字段（脱敏后再入备份）。

版本：

- `manifest.json` 必须包含 `backupVersion`、`appVersion`、`createdAt`、各文件条目清单与校验值。
- 恢复时若 `backupVersion` 高于当前支持的版本 → 拒绝并提示；低于当前版本 → 按定义的迁移路径升级后导入。

恢复模式（三模式必须定义冲突规则）：

- **Merge**：以 `id` 为主键；同一 `id` 已存在时，比较 `updatedAt`，较新者胜；`updatedAt` 相同则保留本地记录并将冲突写入恢复报告。用户受保护字段（field_edits）不得被备份数据覆盖。
- **Replace**：清空当前 transactions / pending / evidence / duplicate_decisions / capture_logs / field_edits / categories / accounts / budgets / rules，再导入备份内容；设置项按备份内容覆盖。
- **Settings Only**：只恢复设置项（`settings.json` 中的开关、主题、阈值、工作模式等），不触碰任何账务数据。设置项的存储归属见 `04` §6。

失败原子性：

- 恢复必须在事务中执行；任一步失败则整体回滚，当前数据保持恢复前状态。
- 损坏备份（无法解压、manifest 校验失败、JSON 解析失败）必须拒绝导入并提示，且不得修改现有数据。
- 恢复完成后必须给用户一份恢复报告（新增 / 更新 / 冲突 / 跳过数量）。

## 18. 隐私

默认：

- 核心账务本地处理
- 原始通知不上传
- OCR 临时截图处理后删除
- 敏感日志脱敏
- AI 默认关闭
- **声明 `INTERNET` 权限，仅用于与本机识别服务的回环通信**（`127.0.0.1`），不用于上传账务数据
- 与网络相关的能力（检查更新、GitHub、邮件反馈）在 v0.1 不提供（**产品范围决定**，与权限无关）

内嵌采集核心数据边界：

- 内嵌采集核心产生的原始数据不得上传任何服务器（含本机回环服务之外的一切网络出口）。
- 若未来引入外部 AI：必须明确提示用户、单独授权、定义发送的数据范围、提供关闭方式，并在引入时同步修改本节与 `07` §12。

### 18.1 应用边界（单 APK 的权限口径）

**单 APK 方案下，采集核心内嵌于账然 APK**，因此其声明即为账然 APK 的声明；不再存在"上游独立安装的应用，账然无权约束"的情形（`07` §9 权限矩阵为准）。

因此：

- 界面说明必须区分**用途**而非主体，例如"账然声明 `INTERNET`，**仅用于与本机识别服务的回环通信**；账务数据不出本机"。
- **可以**声明"账务数据不出本机"；但**不得**声明"不申请网络权限"或"整个方案不联网"（账然自身已声明 `INTERNET`）。
- 账然自身 Manifest 的权限清单要求见 `07` §9（并按 `07` §9.1 区分"领域层是否需要"）。

## 19. 采集工作模式与权限

采集由**内嵌的采集核心**（AutoAccounting，Gradle 模块）提供，账然按工作模式决定接入方式与所需权限。

- 产品要求：必须提供工作模式选择与对应的权限引导，且不得展示与当前模式无关的权限。
- 权限与工作模式的权威定义：`07_自动记账与AutoAccounting集成.md` §9（本表仅为产品视角摘要，如与 `07` 不一致以 `07` 为准）。
- **下列权限由账然 APK 自身声明**（单 APK；见 §18.1）。

| 工作模式 | 采集来源 | 账然所需权限 / 条件 |
|---|---|---|
| ~~LSPosed 模式~~ | Hook 系统通知、Hook 应用内数据 | **内嵌后不支持**（已剥离 Xposed 身份，且目标设备无 Root） |
| 通知渠道（基础） | 通知监听 | `POST_NOTIFICATIONS`、`FOREGROUND_SERVICE`（含 `_SPECIAL_USE`）、`INTERNET`（本机回环识别） |
| OCR 模式 | 无障碍 / Shizuku 截图识别 | 无障碍服务或 Shizuku + 截图能力（Shizuku 由用户授权） |
| 短信模式（可选） | 短信广播 | `RECEIVE_SMS` / `READ_SMS` |
| 悬浮窗 / 记账面板（D3） | Pending 确认与编辑入口 | `SYSTEM_ALERT_WINDOW`（可选） |
| 手工模式 | 用户手工记账 | 无 |

- 电池优化豁免为**建议项**，不是必需项。
- 权限引导页必须按所选工作模式展示对应步骤，不得展示与当前模式无关的权限。
- 权限被撤销时：自动记账状态必须显式变为不可用，并在首页与自动记账页提示；已捕获未处理的 Pending 保留不变。

## 20. 捕获日志

- 展示字段：时间、来源（CaptureSource）、包名、上游规则/版本、状态、confidence、reason。
- 状态取值至少包含：`CAPTURED`、`PARSED`、`PENDING`、`CONFIRMED`、`IGNORED`（用户忽略）、`IGNORED_INVALID`（系统判定无效）、`RULE_TEST`、`FAILED`。
- 状态取值的落库 SSOT 为 `03` §19（本清单是其子集，`03` §19 另含 `DUPLICATE`、`VERSION_MISMATCH` 等）。
- 支持状态筛选、来源筛选、关键词搜索。
- 保留策略：最多保留 1000 条或最近 90 天，以先到者为准；超出后按时间从旧到新清理。
- 清空日志的效果：只清空日志与原始捕获证据；**不影响**任何 Transaction、Pending 的处理状态与字段保护标记。
- 脱敏字段（必须脱敏后才能展示与落库）：完整账号、完整手机号、完整银行卡号、身份证号、支付单号中间段、通知中的个人姓名（保留姓氏 + `**`）。

## 21. 采集健康度

为避免采集静默失效导致漏账：

- 连续 24 小时无任何捕获事件（且自动记账开关为开启）时，自动记账状态必须变为“疑似失效”，并在首页与自动记账页提示用户。
- 连续 72 小时无任何捕获事件时，必须给出明确的排查引导（权限、模式、采集核心状态）。
- 用户主动关闭自动记账时不触发上述提示。
- “疑似失效”为状态提示，不得因此自动创建任何 Pending 记录。

## 22. 降级与保底能力

手动记账是账然的**保底能力**，不依赖任何采集权限与采集核心。

规则：

- 手动记账（EXPENSE / INCOME / TRANSFER / REFUND）**不得依赖**通知权限、无障碍、Shizuku、采集核心初始化成功等任何条件。
- 采集核心**未授权 / 未初始化 / 初始化失败 / 运行中失效**时，以下功能必须**全部保持可用**：
  手工记账、账务列表、交易详情、分类管理、账户管理、统计、预算、备份与恢复。
- 采集失效**只影响**“自动捕获”这一项能力；界面必须显式展示采集状态（不可用/疑似失效），
  不得静默伪装为正常，也不得因采集异常而崩溃或阻止进入记账主流程。
- 应用启动**不得被采集核心阻塞**：采集核心初始化失败时，App 必须仍能进入首页并完成一次手工记账。
- 上述降级行为属于**产品承诺**，不是“可选优化”。
