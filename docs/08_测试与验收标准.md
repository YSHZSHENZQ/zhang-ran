# 08 测试与验收标准

版本：v0.1  
定位：本文件定义可执行的测试与验收判据。每条判据必须能对应到 `02`/`03`/`04`/`06`/`07` 中的一条规则；若某条规则在本文件中没有判据，视为未验收。

## 1. 测试原则

优先级：

```text
正确性
>
数据安全
>
可恢复
>
稳定性
>
可维护性
>
自动化率
>
性能
```

核心验收原则：

> 宁可 Pending，也不要错误自动入账。

补充原则：

- 禁止只测 Parser 而不测最终结果。
- 每条业务规则必须有断言形式的验收（期望值 + 状态 + reason）。
- 当前阶段（纯文档、无 Android 工程）不具备执行条件；本文件的 DoD 从**编码开始的第一个提交**起生效。

## 2. Unit Test

### 2.1 Money（`03` §4）

金额单位以“分”为准，断言必须写具体数值：

| 输入 | 期望 `amountMinor` |
|---|---|
| ¥0 | 0 |
| ¥0.01 | 1 |
| ¥1 | 100 |
| ¥12.34 | 1234 |
| ¥100 | 10000 |
| ¥999999.99 | 99999999 |
| `1,234.56`（千分位） | 123456 |
| 非法（`"abc"`、`"--1"`、空串） | 解析失败，不得产生 CONFIRMED |

补充断言：

- `amountMinor < 0` 必须被拒绝。
- 任何路径不得出现 `Double` / `Float` 参与金额存储与最终运算。

### 2.2 Transaction 类型（`03` §5/§13）

- EXPENSE：`sourceAccountId = null`、`targetAccountId = null`、`relatedTransactionId = null`
- INCOME：同上
- TRANSFER：`sourceAccountId` 与 `targetAccountId` 非空且不相同；`categoryId = null`
- REFUND：`relatedTransactionId` 非空；累计退款金额 ≤ 原交易金额

### 2.3 Decision（`03` §16）

| 场景 | 期望 |
|---|---|
| 全字段齐备、`overallConfidence = 0.8` | CONFIRMED |
| 全字段齐备、`overallConfidence = 0.79` | PENDING + LOW_CONFIDENCE |
| `amountMinor` 缺失 | PENDING + AMOUNT_UNCERTAIN |
| `amountConfidence = 0.49` | PENDING + AMOUNT_UNCERTAIN |
| `direction` 缺失 | PENDING + DIRECTION_UNCERTAIN |
| 分类未确定（金额方向明确） | PENDING + CATEGORY_UNCERTAIN |
| 账户无法匹配 | PENDING + ACCOUNT_UNCERTAIN |
| `currency = USD` | PENDING + AMOUNT_UNCERTAIN |
| 无任何可用字段 | 不产生 Transaction，写捕获日志 IGNORED_INVALID |
| 候选值与被保护字段冲突 | 保留用户值，冲突记入证据，状态按规则判定 |
| `transactionTime` 缺失（`<= 0`）但金额与方向明确 | PENDING + UNSUPPORTED_NOTIFICATION（**不得** CONFIRMED） |

- 必须验证：Decision 是唯一产出状态的环节；Adapter / Normalize / Confidence / Dedup 均不得直接产出状态。

### 2.4 Rule（`02` §16）

- priority：数值小者优先；两条规则同时命中时取 priority 小者，另一条写入证据
- include 命中且 exclude 未命中 → 命中
- include 命中但 exclude 命中 → 不命中，且被拒关键词进入 `rejectedKeywords`
- exact / contains / regex 三种匹配方式各自断言
- 大小写不敏感；全角与半角等价
- direction 与规则方向不符 → 不命中
- `engineVersion` 必须写入候选与证据

### 2.5 Dedup（`03` §12）

| 场景 | 期望 |
|---|---|
| `externalTransactionId` 相同 | DUPLICATE |
| 渠道单号相同、捕获时间差 ≤ 24h | DUPLICATE |
| 渠道单号相同、捕获时间差 > 24h | 不判重 |
| `amountMinor` 相同、时间差 ≤ 180s、规范化商户相同 | DUPLICATE |
| `amountMinor` 相同、时间差 ≤ 180s、direction+account 相同 | DUPLICATE |
| `amountMinor` 相同、时间差 ≤ 180s、商户不同且 account 不同 | POSSIBLE_DUPLICATE → PENDING |
| 同商户同金额、时间差 10 分钟 | 不判重 |
| 金额相同、商户不同、时间相近 | 不判重 |
| 时间相近（≤180s）、金额不同 | 不判重 |
| EXPENSE 与 REFUND 之间 | 永不互相判重 |
| 与 7 天前的交易比较 | 不参与判重 |

## 3. Pipeline Test（`03` §1、`04` §2）

测试完整链路：

```text
上游事件
→ capture/（落库 + Envelope）
→ Adapter（Candidate + Evidence）
→ Normalize
→ Confidence
→ Dedup
→ Decision
→ Pending / Confirmed / Duplicate / ClearlyInvalid
→ Repository → Room
```

断言：

- 每一步的输出类型与 `03` 一致。
- 任一步失败时有明确终态（Pending 或捕获日志 FAILED），不得静默丢弃。
- 禁止只测试上游解析而不测试最终落库结果。

## 4. Pending Test（`02` §4/§5、`03` §16）

必须验证每个 reason 的触发与 UI 动作集：

| reason | 触发条件 | 期望动作集 |
|---|---|---|
| UNKNOWN_MERCHANT | merchant 缺失或 confidence 不足 | 编辑后入账 / 忽略 |
| AMOUNT_UNCERTAIN | 金额缺失或 confidence < 0.5 或 currency ≠ CNY | 编辑后入账 / 忽略 |
| DIRECTION_UNCERTAIN | direction 缺失或 confidence < 0.5 | 编辑后入账 / 忽略 |
| CATEGORY_UNCERTAIN | 分类未确定 | 编辑后入账 / 忽略 |
| ACCOUNT_UNCERTAIN | 账户无法匹配 | 编辑后入账 / 忽略 |
| POSSIBLE_DUPLICATE | 语义兜底条件不完整 | 查看重复 / 忽略 |
| REFUND_UNCERTAIN | 无法确定原交易或累计超额 | 编辑后入账 / 忽略 |
| TRANSFER_UNCERTAIN | 无法确定转入/转出账户 | 编辑后入账 / 忽略 |
| UNSUPPORTED_NOTIFICATION | 上游未识别结果不可用 | 编辑后入账 / 忽略 |
| LOW_CONFIDENCE | `overallConfidence < 0.8` | 编辑后入账 / 忽略 |

补充断言：

- 多个 reason 并存时全部落库，UI 展示严重度最高者，详情可见全部。
- 忽略后状态为 IGNORED，证据保留，可从日志恢复为 PENDING，不计入统计。
- Pending 不会被自动清理或自动消失。

## 5. User Edit Test（`03` §11、`02` §5）

字段级保护：

```text
自动识别 → Pending → 用户修改分类 → 保存并入账 → 再次运行规则/上游重新识别
```

断言：

- 分类保持用户值；只产生 `FieldEdit(categoryId)`，不产生其他字段的 FieldEdit。
- 再次运行自动流程后，`merchant` / `amountMinor` 等未修改字段仍可被更新（若其值有变化），但 `categoryId` 不得被覆盖。
- 被保护字段被判为不可靠时，不得被清空或改写；只允许新增 Pending 建议项。

“未修改直接确认”：

```text
Pending → 不做任何修改 → 点击保存并入账
```

断言：

- `confirmedByUser = true`
- `FieldEdit` 数量为 0
- 后续自动流程可继续更新该交易的非用户字段

转账字段保护：

```text
自动识别/手工创建转账 → 用户修改转入账户 → 保存 → 再次运行自动流程
```

断言：

- 产生 `FieldEdit(targetAccountId)`（`03` §11 的 fieldName 枚举包含 `sourceAccountId` / `targetAccountId`）
- 再次运行自动流程后，转入账户保持用户值，不得被覆盖

## 6. Refund Test（`02` §7/§14、`03` §13）

- 原交易存在时，退款成功关联 `relatedTransactionId`
- 部分退款：退款金额 ≤ 原交易金额
- 累计退款：多次退款累计 ≤ 原交易金额；超出时必须进入 PENDING + REFUND_UNCERTAIN
- 统计：`当月消费 = ΣEXPENSE − ΣREFUND`（同一分类内冲减）
- 退款发生在不同月份时，冲减**退款发生月**，不改动原交易月份统计
- 退款不占用预算，并释放对应分类已用额度
- 原交易被删除后：退款保留且 `orphan = true`，并进入 Pending
- 退款不得产生额外消费

## 7. Transfer Test（`02` §8、`03` §13）

- `sourceAccountId` / `targetAccountId` 必填且不相同
- `categoryId` 必须为空
- 两侧账户余额各变化一次
- 不进入本月支出 / 收入 / 结余
- 不进入消费统计与预算占用
- 账户相同的转账必须被拒绝

## 8. Duplicate Test

- `externalTransactionId` 相同 → DUPLICATE
- merchant 相同 + amount 相同 + 时间不同（> 180s）→ 不判 DUPLICATE
- “这是同一笔”：新候选状态为 DUPLICATE，候选与证据保留，`DuplicateDecision` 落库
- “这是两笔不同交易”：候选进入编辑入账流程，原记录不变
- 撤销重复判定：DUPLICATE → PENDING 迁移成功
- 比较范围：与 8 天前的同商户同金额交易比较 → 不参与判重（不判 DUPLICATE）
- 捕获级去抖：同一 `packageName + notificationId + postTime` 连续投递两次 → 只产生一条捕获记录与一条候选，不产生两条交易
- 缺失 identity：无 `externalTransactionId`、无 notification identity，仅 merchant + amount 相同但时间差 > 180s → 不判重（保持两条独立记录）
- 缺失 identity 且无法确定是否同一次投递 → 进入 PENDING，不得自动判重或自动丢弃
- 判重结论与状态决定分离：Dedup 只产出 `Duplicate` / `PossibleDuplicate` / `NoDuplicate`，最终状态只能由 Decision 写出（断言 Dedup 层不写 `TransactionState`）

## 10. Backup Test（`02` §17）

### Backup

- 生成 `zhangran-backup-v1-<yyyymmdd>.zip`
- 包含：manifest / transactions / categories / accounts / budgets / rules / pending / evidence / duplicate_decisions / capture_logs / field_edits / settings
- manifest 含 `backupVersion`、`appVersion`、`createdAt`、文件清单与校验值

### Restore Merge

- 原数据保留，新数据合并
- 同 `id` 冲突：`updatedAt` 较新者胜；相同则保留本地并写入恢复报告
- 本地受保护字段（field_edits）不被备份数据覆盖
- 恢复报告包含新增 / 更新 / 冲突 / 跳过数量

### Restore Replace

- 按 `02` §17 定义的范围清空后导入
- 清空范围包含 pending / evidence / duplicate_decisions / capture_logs / field_edits

### Settings Only

- 只恢复设置项，账务数据零变化（可用记录数与 hash 断言）

### Corrupt Backup

- 无法解压 / manifest 校验失败 / JSON 解析失败 → 拒绝导入
- 当前数据库内容与恢复前完全一致（逐表断言）

### Restore 失败原子性

- 导入中途失败（模拟磁盘满 / 中途抛异常）→ 全部回滚，数据与恢复前一致

### 版本兼容

- `backupVersion` 高于当前支持 → 拒绝并提示
- `backupVersion` 低于当前支持 → 走迁移路径后导入成功

## 11. Budget / Stats Test（`02` §11/§12/§14、`03` §9）

### 11.1 预算

- 总预算（`scope = TOTAL`）与分类预算（`scope = CATEGORY`）互相独立：总预算未超而分类预算超额时，只提示分类超支，不因总预算而改变分类结论。
- `periodKey` 唯一性：同一月份只能有一条 TOTAL 预算；同一月份 + 同一分类只能有一条 CATEGORY 预算。
- PENDING 交易不占用额度：创建 Pending 后已用金额不变。
- CONFIRMED 交易占用额度：已用金额按 `02` §12 增加。
- DELETED 交易回滚额度：删除后已用金额回到删除前的值。
- REFUND 释放额度：退款后对应分类与总额的已用金额减少对应数额。
- TRANSFER 不影响任何预算数字。
- 超支仅视觉提示：超支时数据写入正常，不出现阻塞或强制弹窗。
- Pending 中的记录不因超支而被自动处理。

### 11.2 统计

- 只计入 CONFIRMED；PENDING / IGNORED / DELETED / 系统判定无效均不计入。
- `当月消费 = ΣEXPENSE − ΣREFUND`（同分类内冲减；退款分类不明确时冲减总额）。
- `当月收入 = ΣINCOME`；`当月结余 = 当月收入 − 当月消费`。
- TRANSFER 不计入支出、收入、结余与消费统计；仅影响账户余额流水。
- 退款发生在不同月份时：只冲减退款发生月，不改动原交易月份的数字。
- 趋势图与分类占比与上述口径一致（不含 PENDING / IGNORED / DELETED / TRANSFER）。
- 月末边界按 `transactionTimeZone` 判定归属月份，跨时区不会把交易计入相邻月份。

## 16. Capture Fixture

每一种真实通知 / 识别结果都应形成 fixture。

格式要求：

```text
fixtures/
├── manifest.json          // fixture 列表、来源、模式、期望结果
├── wechat/
│   ├── payment.json       // 输入事件原文（脱敏）
│   └── payment.expected.json // 期望候选字段 + 期望状态 + 期望 reason
├── alipay/
├── refund/
├── transfer/
├── historical_replay/     // 历史回灌用例
└── ambiguous/
```

约束：

- 每个 fixture 必须包含 `expected`（期望候选字段、期望状态、期望 reason），否则不构成测试用例。
- 必须包含至少一个历史回灌用例（`isHistoricalReplay = true` → 不得 CONFIRMED）。
- fixture 不得包含真实个人敏感数据，按 `02` §20 脱敏。
- 单一 fixture 文件建议 < 64 KB，避免仓库膨胀。

## 17. 采集核心集成测试（进程内接口）

前置：`07` §3.5 的**进程内接口**；采集核心的硬事实与版本锚点见 `10`（§5 关键事实、§8 待确认项、§9 升级复核点）。每条用例必须记录**采集核心的来源 commit**。

### 17.1 连通（进程内）

> **本节已按单 APK 重写**：原"契约与连通"用例（scheme 可解析 / 无界面入口 / 入口无业务 / 无回执语义 /
> 上游未安装 / 版本不匹配）的**对象已不存在**（URI scheme 与接收入口 Activity 已按 D7 删除；
> 采集核心与领域层同进程）。历史实测记录见 `11`（只加不改）。

| 用例 | 输入 / 操作 | 期望 |
|---|---|---|
| 进程内可达 | 采集核心产出一条识别结果 | 经 `capture/` 接入层被接收，产出候选与证据 |
| 落库先于处理 | 采集核心产出后立刻杀进程再启动 | 事件已在 `capture_logs` / `evidence` 中（先落库再处理） |
| 提交不随页面结束丢事件 | 触发采集后立即退出相关页面 | 记录仍落库（提交走应用级作用域，见 `docs/09` §7） |
| 不经 URI / Intent | 审查实现 | 无 `zhangran://` 接收 Activity、无 scheme 声明（`07` §3.5） |
| 采集核心不得直写业务库 | 审查实现 | 采集核心无账然 Repository / DAO 引用；`transactions` 只经 Domain 写入 |
| 接口版本不匹配 | 构造接口版本不一致 | 写 `CaptureLog` + 一律 Pending，不按旧接口解析入账 |

### 17.2 字段与类型映射（对齐 `03` §18）

| 用例 | 输入 | 期望 |
|---|---|---|
| 支出 | `type=Expend, money=26.5` | `amountMinor=2650`、`EXPENSE` |
| 分位精度 | `money=0.01` / `999999.99` | `1` / `99999999` |
| Double 陷阱 | `money=8.7` | `870`（用 `BigDecimal(toString())`，不得用 `8.7*100`） |
| 手续费 / 优惠 | `fee=-1.0` / `fee=1.0` | 分别识别为手续费 / 优惠；**原 `money` 与上游对象不得被改动** |
| 收入 | `type=Income` | `INCOME` |
| 转账 | `type=Transfer` 且 `accountNameTo` 非空 | `TRANSFER`、`categoryId=null`、两侧账户非空 |
| 转账缺目标账户 | `accountNameTo` 为空 | Pending（`TRANSFER_UNCERTAIN`） |
| 退款 | `type=IncomeRefund` | `REFUND` + `relatedTransactionId`；无法关联 → Pending（`REFUND_UNCERTAIN`） |
| 借贷 / 还款 | `ExpendLending` / `ExpendRepayment` / `IncomeLending` / `IncomeRepayment` | **一律 Pending**（`DIRECTION_UNCERTAIN`），不得入账 |
| 报销 | `ExpendReimbursement` / `IncomeReimbursement` | **一律 Pending**，不得当作退款或支出入账 |
| 未知类型 | 上游新增未映射取值 | Pending（`UNSUPPORTED_NOTIFICATION`） |
| 时区补齐 | 上游 `time` 无时区信息 | `transactionTime` 为 UTC millis 且 `transactionTimeZone` 非空；跨日归属正确 |
| 币种 | `currency` 含 `rate` 且非 CNY | 丢弃 `rate`、不换算 → Pending（`AMOUNT_UNCERTAIN`） |
| 分类父子 | `cateName` 含父子分隔符 | 拆分为 `categoryHint`；映射不到 → `CATEGORY_UNCERTAIN` |
| 账户名称映射 | `accountNameFrom` 无对应账户 | `ACCOUNT_UNCERTAIN` + Pending，保留 `accountHint` |
| 上游状态不外泄 | `state=Wait2Edit` 等 | 不得写入账然 `state` |
| `groupId` 不判重 | 上游已合并的同组账单 | 不得据此判 `DUPLICATE`，仍按 `03` §12 判定 |
| 来源映射 | `app` / `channel` 各取值 | 映射到 `07` §5 枚举；不得新增枚举值 |

### 17.3 架构与权限

- 账然 Manifest 的权限与 `07` §9 权限矩阵**逐项一致**（**含 `INTERNET`**，因识别经本机回环通信，D1）；无重复的采集类服务声明。
- 内嵌采集核心的 Room 库文件与账然库文件**完全隔离**（D4：文件名不同、不共用、不互读）；备份只覆盖账然账务数据。
- `data/**` 与账然 `domain/**` 不得 import 采集核心的 UI 类（`07` §16、`04` §9.1）。
- 采集核心以 Gradle 模块内嵌（D6），来源 commit 与 LICENSE 已记录（`10` §1、`07` §20）；**无独立补丁仓**。
- 采集核心升级后重跑本节的 17.1/17.2 全部用例（`07` §22）。

## 18. 权限测试（按工作模式）

- 采集核心未初始化（首次启动 / 初始化失败）→ 自动记账状态不可用并提示
- Xposed 模式：**内嵌后不支持**（D6-b 已剥离身份，且目标设备无 Root）——本项标注"不适用"，不得伪报通过
- OCR 模式：无障碍未授权、Shizuku 未授权 → 各自独立提示（授权对象为账然自身）
- 权限被撤销：自动记账状态显式变为不可用；已捕获 Pending 保留不变
- 用户关闭自动记账：不触发权限提示与健康度提示
- 引导页主体正确：步骤文案指向**本应用自身**的权限（无障碍 / Shizuku / 通知），且与 Manifest 实际声明一致
- 应用必须明确显示状态，不得静默表现为正常
- 撤销采集相关权限（通知 / 无障碍 / Shizuku）后：App 不崩溃、不阻塞启动、不阻止手动记账；仅自动记账状态变为不可用（`02` §22）

## 19. 数据安全测试

验证：

- 用户修改不会丢失（字段级保护）
- 数据库升级不丢数据
- Backup 可恢复
- 损坏备份不破坏现有数据
- 敏感日志已脱敏，脱敏字段清单与 `02` §20 一致
- 系统判定无效的记录写日志且不产生 Transaction
- 清空日志不影响 Transaction、Pending 状态与字段保护标记
- 日志保留策略：写入第 1001 条或超过 90 天的记录后，按时间从旧到新清理，且清理不影响交易数据
- 清空所有数据：按 `02` §17/§20 的范围清空账务、Pending、证据、日志与规则，并保持数据库可继续写入
- 应用边界说明：界面文案明确“账然声明 INTERNET **仅用于与本机识别服务的回环通信**，账务数据不出本机”；**不得宣称“不申请网络权限”**（D1、`02` §18.1）

## 20. 性能

MVP 不以极限性能为目标。

重点：

- 大量交易搜索（以 ≥ 10,000 条交易为参考量级）

不设硬性指标，但必须记录基线数据供后续对比。
